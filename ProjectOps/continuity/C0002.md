### Evidencia recuperada de la rama histórica

El trabajo previo no se repite ciegamente. Se recuperó la siguiente evidencia:

1. El probe final instaló `vitest@4.1.11` en todos sus candidatos.
2. El candidato `vitest-only` llegó hasta `pnpm audit` y falló allí porque `stream-json` seguía vulnerable; ese rojo NO demuestra incompatibilidad de Vitest 4.
3. El candidato `stream-json-patched` mantuvo el `@solana/web3.js` vigente, añadió override selectivo `stream-json@<=3.4.0 -> 3.6.0` y, junto con Vitest 4.1.11, pasó en Node 22:
   - `pnpm audit`;
   - smoke Solana JSON-RPC;
   - typecheck;
   - build;
   - full `test:ci`.
4. El candidato `solana-latest-stream-json-patched` también pasó, pero elevar Solana no es necesario si el override selectivo conserva el parent actual y ya demuestra compatibilidad.
5. Por tanto, actualizar `@solana/web3.js` sólo para resolver este advisory aumenta superficie sin evidencia de beneficio necesario y no es la ruta preferida.

### Verificación externa de compatibilidad

La guía oficial de migración de Vitest 4 declara Node.js >=20 y Vite >=6 como prerequisitos. Los breaking changes materiales afectan mocks, pools y APIs/config deprecated. La validación real del repo sigue siendo obligatoria; documentación upstream no sustituye CI ABOS.

### Hipótesis principal

Remediación mínima coherente:

- elevar la dependencia directa `vitest` a `4.1.11` o versión 4.x patched equivalente auditada;
- añadir override selectivo sólo para versiones vulnerables de `stream-json` (`stream-json@<=3.4.0` -> `3.6.0`);
- regenerar lockfile con pnpm autoritativo;
- no elevar Solana salvo que una prueba actual lo exija;
- ejecutar gates completos en Node 20/22 y Windows.

### Hipótesis alternativas / falsación

- H-alt-1: Vitest 4 rompe mocks/config/tests en ABOS aunque el probe Node 22 haya pasado. Se discrimina con full CI Node 20/22.
- H-alt-2: el override `stream-json` rompe JSON-RPC de Solana. Se discrimina con smoke realista + suites identity/wallet y full CI.
- H-alt-3: el dependency graph de `main` cambió desde la rama histórica y la solución ya no aplica. Se discrimina regenerando lockfile desde esta base y ejecutando `pnpm audit` actual.

### Semántica a preservar
