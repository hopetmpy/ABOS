### Grafo authority / producers / consumers reconstruido

- Generic capability authority: `CapabilityRegistry`, único y en memoria, reconstruido por `runAgentLoop()`.
- Producers: built-in/runtime tool definitions, installed-tool inventory, loaded skills y `EnvironmentSnapshot.capabilities`.
- Producer evidence-rich: environment providers mediante `inspect()`; availability, evidence y `observedAt` se proyectan al registry, no a una authority paralela.
- Consumers operativos: `CapabilityResolver`, `resolve_capability`, planner/orchestrator y paths de resolution.
- Consumer paralelo de claims: system prompt, CLI/status y list surfaces.
- Persistence: generic registry no durable; installed tools y skills son inventory durable, por lo que restart no puede promoverlos a readiness sin observación actual.
- Environment resource lifecycle sí es durable mediante `EnvironmentResourceStore`; no es una segunda generic capability authority.

### Hallazgos confirmados

1. `available: boolean` era insuficiente para representar provenance/lifecycle.
2. Tool definition, installed/enabled y skill enabled no equivalen a runtime readiness.
3. `CapabilityResolver.use_existing` debe exigir `VERIFIED_AVAILABLE`, no mera existencia.
4. `src/environments/` ya contiene availability/evidence/observedAt reutilizable.
5. Persisted skills requerían revalidación de requisitos actuales después de restart.
6. System prompt y planner contenían claims estáticos que confundían soporte arquitectónico con disponibilidad actual.
7. Child-balance UNKNOWN debía preservarse según P-003; no autoriza autofunding.
8. Installed MCP era nominal: existía configuración/enablement mientras el executor devolvía texto de aparente invocación sin ejecutar protocolo MCP.
9. P-015 conserva la implementación MCP real; P-008 sólo debe impedir claims/readiness/success ficticios antes de esa frontera.
10. CLI `--status` ya usa semántica de inventario para tools y skills; no necesita fingir probes runtime.
11. `EnvironmentSelector` admite `degraded` con score menor. No se cambió: degraded puede seguir siendo operacional; P-008 no autoriza colapsarlo a unavailable sin contrato adicional.

### Hallazgo falsado

La conclusión preliminar «`loadInstalledTools()` no filtra disabled» fue FALSADA.

`AbosDatabase.getInstalledTools()` ya ejecuta `SELECT * FROM installed_tools WHERE enabled = 1`.

Conclusión correcta: **enabled/installed es inventario administrativo; no es prueba de `VERIFIED_AVAILABLE`**.

### Hipótesis competidoras — resolución

- H1 — CONFIRMADA: el booleano legacy y la promoción por existencia causaban overclaim.
- H2 — PARCIALMENTE FALSADA / REUSE: no existe otra generic authority que deba sustituir `CapabilityRegistry`; la evidence rica de environments debe proyectarse en él.
- H3 — CONFIRMADA: `available` puede sobrevivir sólo como proyección backward-compatible.
- H4 — CONFIRMADA PARCIALMENTE: producers con probes actuales pueden elevar disponibilidad; inventario por sí solo no.
- H5 — FALSADA: disabled installed tools ya estaban filtradas por la DB.
- H6 — CONFIRMADA: MCP nominal era una ruta real de false-success y debía cerrarse sin preimplementar P-015.

### DECISION_READY

Clasificación dominante: **EXTEND + UNIFY + CORRECT**, no CREATE.

1. Mantener `CapabilityRegistry` como única authority genérica.
2. Extender capability truth con lifecycle, evidence, authority y temporalidad.
3. Requerir evidence no vacía + `observedAt` válido para aceptar `verified_available`.
4. Conservar legacy `available` únicamente como proyección derivada.
5. Tool/skill existence se registra como discovered/unverified salvo producer evidence-rich.
6. Proyectar `EnvironmentSnapshot` con `registerEnvironmentSnapshot()` para conservar availability/evidence/observedAt.
7. Resolver sólo produce `use_existing` desde current verified evidence.
8. Preservar UNKNOWN, UNAUTHORIZED y PROHIBITED como estados distintos.
9. P-008 corrige claims y ejecución nominal; P-014 implementará fabric más amplio y P-015 el protocolo MCP real.
