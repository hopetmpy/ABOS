### Estado encontrado antes de source

P-008 exige separar source/install/discovery de disponibilidad verificada. La auditoría del Required-Context y dependencias materiales encontró:

1. `src/capabilities/model.ts` representa disponibilidad con `available: boolean`, sin provenance/lifecycle suficiente para distinguir discovered/acquired/probed/verified/degraded/unauthorized/prohibited/unknown.
2. `CapabilityRegistry.ingestTools()` registra toda tool entregada al registry con `available: true` únicamente por existir en la colección.
3. `CapabilityRegistry.ingestSkills()` trata `enabled !== false` como disponibilidad.
4. `CapabilityResolver` usa ese booleano para producir `use_existing`, por lo que una sobrepromoción upstream se convierte en claim operativo.
5. `createCapabilityTools()` incorpora snapshots de environments directamente al registry sin proyectar explícitamente `EnvironmentSnapshot.availability`, evidence y observedAt a un lifecycle de capability.
6. `runAgentLoop()` crea un único `CapabilityRegistry` por runtime y lo alimenta con built-ins, installed tools, environment tools, skills y environment snapshots. No existe una segunda authority genérica de capabilities que deba reemplazarlo.
7. `src/environments/` sí posee semántica más rica y reusable: availability del environment, evidence, observedAt y lifecycle persistente de resources. Esa evidencia debe alimentar el registry, no competir con él.
8. `loadInstalledTools()` no filtra `enabled`; todo registro de `installed_tools` se convierte en `AbosTool`.
9. El executor MCP de `loadInstalledTools()` no ejecuta protocolo MCP: devuelve una cadena que afirma que la tool fue invocada. P-015 sigue siendo la frontera de MCP real; P-008 debe impedir que esta configuración nominal sea anunciada como capacidad verificada.
10. `InstalledTool` sólo conserva installed/enabled. `installMcpServer()` persiste configuración como enabled sin probe; installed/enabled no es availability.
11. `loadSkills()` sí prueba bins/env para skills encontradas en disco, pero al final devuelve todos los skills enabled de DB, incluidos DB-only/stale que ya no fueron observados en el filesystem actual.
12. `buildSystemPrompt()` contiene claims estáticos amplios (`What you have`, `You CAN`) y etiqueta todas las tool definitions como `AVAILABLE TOOLS`, aunque su readiness externa no haya sido probada.
13. El bloque estático de child health todavía describe `Credit balance < 10 cents -> out_of_credits` y autofunding como si el balance fuese siempre observable; P-003 demostró que child balance puede ser UNKNOWN y que no debe autofondearse desde UNKNOWN.
14. Los tests actuales de capability registry/resolver validan `available: true` escrito manualmente, pero no cubren provenance, freshness, degradation, unauthorized, restart ni installed-vs-verified.
15. GitHub code search devolvió `incomplete_results=true`; ningún resultado vacío se usó como prueba de ausencia.

### Authority / producer / consumer graph reconstruido

- Generic capability authority: `CapabilityRegistry` en memoria, reconstruido en cada `runAgentLoop()`.
- Producers: runtime tool definitions, installed tool rows, loaded skills, `EnvironmentSnapshot.capabilities`.
- Evidence-rich producer: environment providers mediante `inspect()`; AWS prueba CLI + STS antes de `availability=available`, Conway prueba balance/API, local observa host/process facts.
- Consumers: `CapabilityResolver`, `resolve_capability`, environment/capability discovery tools y cualquier planner path que use esa resolution.
- Prompt consumer paralelo: `buildSystemPrompt()` recibe `AbosTool[]` directamente y actualmente no consume la authority/evidence del CapabilityRegistry.
- Persistence: generic registry no es durable; se reconstruye en restart. Installed-tool y skill inventory sí es durable y puede reintroducir claims stale si se promociona sin nueva observación.
- Environment resource lifecycle sí es durable mediante `EnvironmentResourceStore`; no debe convertirse en segunda generic capability registry.

### Invariantes

- source/test/install != capability success;
- UNKNOWN no se promociona por optimismo;
- una capability puede degradarse o desaparecer sin borrar historia;
- amplitud no autoriza claims falsos;
- no crear un segundo `CapabilityRegistry`;
- no cerrar providers/capabilities a un enum artificial que impida descubrimiento futuro;
- authority/evidence deben viajar con el claim;
- restart no puede promover disponibilidad por ausencia de evidencia fresca;
- P-008 no debe adelantar la construcción completa de P-014 ni fingir MCP real antes de P-015;
- `available` legacy puede sobrevivir sólo como proyección derivada, no como authority independiente.

### Hipótesis competidoras — resolución

H1 — CONFIRMADA. El booleano `available` y los ingestores actuales son una causa material de overclaim.

H2 — PARCIALMENTE FALSADA / REUTILIZADA. No existe otro lifecycle genérico canónico que deba sustituir el registry. Sí existe semántica rica en `environments` que debe proyectarse al registry como evidence/temporalidad.

H3 — CONFIRMADA. `available` puede mantenerse transitoriamente como proyección backward-compatible derivada de un estado más rico; no debe gobernar resolución por sí solo.

H4 — CONFIRMADA PARCIALMENTE. Algunos producers sí hacen probes reales (por ejemplo AWS inspect con CLI + STS), por lo que no deben degradarse a UNKNOWN; deben conservar su evidencia al entrar al registry. Tool existence, installed rows y enabled skills por sí solos no reciben ese privilegio.

### DECISION_READY — unidad 1

Clasificación: **EXTEND + UNIFY + CORRECT**, no CREATE.

Decisión:

1. Extender `CapabilityDescriptor` con lifecycle abierto, evidence temporal y helpers canónicos.
2. Mantener `available` por compatibilidad, pero derivarlo de `VERIFIED_AVAILABLE`; legacy `available: true` sin state/evidence explícitos se trata conservadoramente como unverified.
3. Hacer que `CapabilityRegistry` sea la única authority genérica y normalice todo ingreso.
4. Añadir una proyección explícita `EnvironmentSnapshot -> CapabilityDescriptor` que combine availability, evidence y observedAt; sólo snapshot/capability actualmente disponible produce `VERIFIED_AVAILABLE`.
5. `CapabilityResolver.use_existing` sólo puede consumir capabilities verificadas; known-but-unverified debe pedir probe/evidence en vez de inventar disponibilidad.
6. Tool/skill ingestion genérica deja de promover existencia/enabled a verified. Las rutas que sí poseen prueba actual deberán declararla explícitamente o llegar por producer evidence-rich.
7. No implementar todavía discovery/acquisition/composition completo de P-014 ni MCP protocol runtime de P-015.
8. Añadir tests adversariales para legacy boolean overclaim, environment degradation/authorization, evidence temporal y restart-style reconstruction.

### Riesgo y rollback

Riesgo principal: hacer que una capability previamente optimista deje de ser `use_existing`, revelando dependencias que asumían disponibilidad sin prueba. Eso es un cambio intencional de verdad, pero debe evitar romper producers que sí tienen evidencia actual.

Rollback semántico seguro: conservar el campo legacy `available` y aceptar descriptors antiguos; ante ausencia del nuevo state se degrada a unverified/unknown en vez de promoverse. No se requiere schema migration porque el registry es in-memory.
