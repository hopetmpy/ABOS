## Auditoría y falsación H1–H6

### H1 — CONFIRMADA, localizada

Existen rutas que persisten lifecycle por intención sin post-condición:

1. `src/orchestration/health-monitor.ts::restartAgent()` sólo envía `shutdown_request`; si el envío no lanza error, escribe `starting`. No ejecuta un start ni observa proceso posterior.
2. `stopAgent()` escribe `stopped` incluso cuando el envío de shutdown devuelve failure.
3. `src/orchestration/messaging.ts` demuestra que el handler estándar de `shutdown_request` es un stub de registro; `LocalDBTransport` sólo inserta un inbox row. Delivery success no demuestra que el child se detuvo.
4. `src/heartbeat/tasks.ts::agent_pool_optimize` escribe `children.status='stopped'` por inactividad sin ejecutar stop y sin atravesar `ChildLifecycle`.
5. `src/__tests__/orchestration/health-monitor.test.ts` institucionaliza el contrato erróneo al considerar restart exitoso con sólo message-send + `starting`.

H1 no es global: `ChildHealthMonitor` y `ensureChildRuntimeRunning()` sí observan el proceso child-scoped antes de `healthy`.

### H2 — CONFIRMADA

El defecto está concentrado en rutas orchestration/heartbeat legacy. Las rutas modernas ya contienen primitivas correctas:
- `ChildHealthMonitor.checkHealth()` usa child-scoped `pgrep`;
- `ensureChildRuntimeRunning()` prueba primero, evita duplicate launch, ejecuta start y re-observa antes de `healthy`;
- environment lifecycle conserva UNKNOWN ante inventory/reconcile ambiguity.

Conclusión: corregir por EXTEND/UNIFY; no reescribir todo lifecycle.

### H3 — PARCIALMENTE CONFIRMADA

Dentro del mismo proceso `DurableScheduler` ya evita overlap tras timeout: mantiene y renueva el lease hasta que la promesa original settle; late success suprime retry.

Gap real: si el runtime muere después del timeout mientras el efecto externo sigue vivo, cesa la renovación del lease. Un retry persistido puede quedar elegible tras expiración sin que exista reconciliación externa genérica previa. P-011 no debe fingir exactly-once; para lifecycle child, las mutaciones implementadas deben ser probe/reconcile-before-act e idempotentes. El hardening genérico de todo side effect externo queda limitado a las authorities que dispongan de reconciliación observable.

### H4 — CONFIRMADA

Ya existen authorities suficientes para construir la corrección sin segundo supervisor:
- `ChildLifecycle` para historia/status;
- child-scoped Conway para observar/actuar proceso;
- `ensureChildRuntimeRunning()` para start idempotente;
- heartbeat leases para overlap en-process;
- environment reconcile para recursos provider-neutral;
- P-010 running/unknown para side effects policy.

Decisión: no crear lifecycle store, supervisor o recovery authority paralelos.

### H5 — CONFIRMADA

`orchestration/health-monitor.ts` contiene dos falsas elevaciones:
- `CRASHED_STATUSES` incluye `unknown`, convirtiendo incertidumbre en `process_crashed`;
- `resolveLastHeartbeat()` mezcla `children.last_checked` —que puede ser timestamp de observación parent— con señales emitidas por el child.

Además `replication/lineage.ts` mantiene un fallback legacy que ejecuta `conway.exec("echo alive")` en la frontera parent/no-scoped y escribe `unknown` directamente fuera de `ChildLifecycle`. No prueba estado child y debe retirarse/unificarse cuando exista monitor canónico.

Decisión: UNKNOWN no dispara restart por sí solo; freshness debe distinguir observación parent de evidencia child.

### H6 — REFUTADA para las rutas auditadas

P-010 persiste `execution_state=running` antes del efecto y conserva incertidumbre si la persistencia final falla. `rate-limits.ts` cuenta `running/succeeded/unknown` como efecto que ocurrió o pudo ocurrir. No se encontró un recovery productivo que consulte `unknown` y lo redispatchee automáticamente como safe-to-retry.

Decisión: preservar P-010 sin crear un retry/recovery paralelo. Cualquier consumidor futuro de `unknown` deberá reconciliar antes de redispatch.

## Semántica de `stopped` y restart

La auditoría de `SandboxCleanup`, `pruneDeadChildren`, `VALID_TRANSITIONS` y tests demuestra que `stopped` es un estado de parada observada con semántica de retiro/cleanup:
- `stopped -> cleaned_up`;
- cleanup acepta stopped/failed;
- pruning incluye stopped como candidato a retiro;
- no existe `stopped -> starting`.

Por tanto abrir `stopped -> starting` degradaría una semántica existente y permitiría que cleanup compita con restart.

Decisión:
- **stop definitivo**: sólo persistir `stopped` después de observar que el proceso ya no existe;
- **restart**: si el proceso estaba/queda offline, mantener/reconciliar lifecycle como `unhealthy` durante la ventana transitoria, iniciar mediante la primitive canónica y sólo persistir `healthy` tras observación;
- no usar `stopped` como midpoint de restart;
- `cleaned_up` permanece terminal.

## Failure matrix

| Caso | Estado/acción correcta |
|---|---|
| proceso ya running al pedir start | observar y reutilizar; no duplicate launch |
| proceso ya stopped al pedir stop definitivo | idempotent success con evidencia; persistir stopped sólo si transición válida |
| shutdown command success pero probe aún running | no declarar stopped; conservar unhealthy/estado previo + failure evidence |
| stop/restart probe falla o sandbox unreachable | UNKNOWN/UNAVAILABLE; no declarar dead/stopped/healthy |
| restart: proceso viejo sigue vivo | no lanzar segundo proceso; reconciliar/stop y volver a observar |
| restart: stop observado, start falla | permanecer unhealthy/failed según evidencia; nunca healthy |
| late start success | post-probe puede reconciliar a healthy sin duplicate start |
| timeout en heartbeat y operación sigue viva | lease in-process se mantiene; crash posterior exige reconcile-before-act |
| parent timestamp sin child evidence | no cuenta como child heartbeat |
| P-010 execution unknown | no redispatch automático; tratar como efecto incierto |
| Conway inventory no observa recurso | resource unknown; ausencia != destrucción |
| cleanup sobre stopped | conserva semántica terminal; no compete con restart |

## Alternativas evaluadas

### A — Crear supervisor/lifecycle authority nuevo
Rechazada: duplicaría ChildLifecycle, heartbeat leases y environment lifecycle; aumentaría autoridad competidora.

### B — Mantener messaging como executor de restart/stop y corregir sólo status
Rechazada: `shutdown_request` no ejecuta el efecto; delivery no es process evidence.

### C — EXTEND/UNIFY replication lifecycle con observación child-scoped
**Seleccionada.** Reutiliza `ChildLifecycle`, Conway scoped client y `ensureChildRuntimeRunning`; orchestration decide que hace falta heal, pero replication ejecuta/reconcilia el proceso real.

### D — Usar EnvironmentLifecycle como única autoridad child-process
Rechazada: EnvironmentLifecycle gobierna recurso/sandbox, no proceso ABOS dentro del child. Sí sirve como patrón semántico y para reconciliar resource availability.

## Decisión técnica — DECISION_READY

Implementación mínima coherente:

1. Añadir dentro de `src/replication/` una primitive canónica de proceso child reutilizando la misma frontera de `ensureChildRuntimeRunning()`; no nueva authority persistente.
2. Extraer/reutilizar un probe child-scoped común para running/stopped/unknown con evidence.
3. Implementar stop definitivo idempotente: probe → child-scoped stop → re-probe → `ChildLifecycle.transition(..., 'stopped')` únicamente tras ausencia observada.
4. Implementar restart idempotente: reconcile/probe → stop si aún running → observar ausencia → mantener `unhealthy` como estado transitorio → llamar/reutilizar start canónico → observar running → `healthy`.
5. Cambiar orchestration `HealthMonitor` para delegar lifecycle effects al executor canónico; message send deja de equivaler a restart/stop success.
6. Cambiar `agent_pool_optimize` para no escribir `stopped` directamente. Debe solicitar/ejecutar stop mediante la misma primitive o, si la frontera no está disponible, registrar intención sin false state.
7. H5: remover `unknown` de crash probado y no usar `last_checked` parent como heartbeat child. Mantener UNKNOWN cuando no existe evidence suficiente.
8. Retirar/unificar el fallback parent-scoped de `refreshChildrenStatus` para no fingir child health.
9. Preservar P-010 `running/unknown`; no crear recovery automático nuevo.
10. No añadir schema/migration salvo que tests demuestren necesidad; preferencia actual: **sin schema change**.
