### Hallazgos ejecutables / clasificación

1. **HECHO — H1 confirmada: write-before-verify.** `editFile()` escribe al source activo y crea commit antes de `pnpm run build`; si build falla devuelve `success: true` con error. El active checkout puede quedar roto mientras el tool call aparenta éxito.
2. **HECHO — pre-snapshot no es snapshot transaccional.** `gitCommit()` usa `git add -A` + `git commit --allow-empty`; además sus errores se ignoran. Puede capturar trabajo sucio ajeno y no garantiza restore.
3. **HECHO — H2 confirmada: no existe journal durable de self-mod transaction.** `modifications` sólo guarda id/timestamp/type/description/file_path/diff/reversible; no transaction id, base/candidate SHA, lifecycle, verification evidence, activation intent, rollback outcome ni lease.
4. **HECHO — hay primitives reutilizables.** SQLite ya expone `runTransaction`; Git local opera sobre `RUNTIME_ROOT`; PolicyEngine ya persiste execution state causal; CI ya cubre Node 22/24, Windows 22/24, full tests, security, rebrand y public smoke. No se crea DB/Git/policy authority paralela.
5. **HECHO — la superficie es mayor que `edit_own_file`.** `revert_last_edit`, `reset_to_upstream` y `pull_upstream` mutan el checkout activo antes de rebuild; `pull_upstream` reconoce explícitamente el estado “code is applied but not compiled” cuando rebuild falla.
6. **HECHO — `exec` puede ser bypass en runtime local.** `ConwayClient.exec()` ejecuta shell real con HOME como cwd; Policy command-safety bloquea guardrails/patrones específicos pero no convierte source mutation ordinaria en transacción. `write_file` también escribe en host HOME en modo local y puede alcanzar un checkout alojado debajo de HOME; su protección actual es de path/core, no transactional safety.
7. **HECHO — ejecución normal intra-turn es secuencial.** `runAgentLoop` usa `for ... await executeTool`, por lo que no hay overlap de tool calls dentro de un mismo loop/turn.
8. **HECHO — concurrencia multi-proceso no está cerrada.** `src/index.ts --run` no adquiere PID/file/self-mod lease global; múltiples procesos podrían compartir DB y checkout. SQLite serializa DB, no filesystem/Git activation.
9. **HECHO — H4 confirmada.** Existen dos thresholds self-mod distintos: `rate.self_mod_hourly = 10` en PolicyEngine y `MAX_MODIFICATIONS_PER_HOUR = 20` en `code.ts`. Son guards duplicados y arbitrarios como safety authority; frecuencia no garantiza recoverability.
10. **HECHO — H6 confirmada.** P-011 aporta recovery/unknown semantics para side effects observables, pero no aislamiento de candidate source, atomic activation ni source rollback.
11. **PARCIAL — H3.** Hay primitives suficientes para EXTEND/UNIFY, pero no una authority transaccional self-mod completa; debe construirse dentro de `src/self-mod/` usando las authorities existentes.

### Alternativas consideradas

A. **Direct write + rollback journal**: mínima refactorización, pero viola el invariante “active source no depende de staging incompleta” y deja demasiadas crash windows. DESCARTADA como authority principal.

B. **Temp files + atomic rename**: útil para un archivo, insuficiente para commits multiarchivo, package/lockfile, build/test aislado y Git/upstream operations. DESCARTADA como unidad canónica.

C. **Git index/tree-only candidate**: buen aislamiento lógico, pero no ofrece filesystem completo natural para install/build/tests sin reconstrucción adicional. No elegida como camino primario.

D. **Copia/clone completo temporal**: fuerte aislamiento, pero duplica repo/metadata, complica auth/origin y disk, y puede copiar por error runtime/secrets si no se filtra. No elegida cuando Git worktree ya resuelve la necesidad.

E. **Git worktree aislado por transacción + journal SQLite + candidate commit verificado + activation condicionada al base SHA**: seleccionada. Usa el mismo repositorio/authority Git, sólo materializa tracked source, permite cambios multiarchivo/dependencias y ejecutar verify antes de active source.

### Decisión canónica — DECISION_READY

Implementar una única authority transaccional en `src/self-mod/` con estas fronteras:

1. **Durable transaction journal, schema v17** dentro de la DB canónica. Estados mínimos: `proposed → staged → verifying → verified → activating → activated`; failure explícito y `rolled_back`/`recovery_required` cuando aplique. Registrar `transaction_id`, request/provenance disponible, `base_sha`, `candidate_sha`, workspace, lease owner/expiry, timestamps, verification evidence/error y rollback/recovery outcome.
2. **Lease persistente de self-mod** adquirida mediante SQLite transaction. Debe impedir double activation entre procesos, expirar/reconciliar tras crash y nunca depender sólo de mutex process-local.
3. **Candidate workspace con `git worktree`** desde `base_sha`, bajo temp dir fuera de `RUNTIME_ROOT` y fuera de `~/.abos`. No copiar wallet/config/state/secrets. Staged changes se aplican allí.
4. **Verification en candidate**, no active checkout: protected scope + diff validation; lockfile/dependency review cuando cambie; frozen install cuando sea necesario; typecheck/build/tests pertinentes; full gates en integración. Failure = no activation.
5. **Candidate commit** sólo después de verificar. La transacción registra el commit exacto que se pretende activar.
6. **Activation compare-and-swap lógico**: antes de tocar active checkout, reconfirmar que `HEAD == base_sha` y que no apareció un estado conflictivo. Si cambió, no forzar ni borrar trabajo: dejar candidate verificable y clasificar `stale_base/conflict` para restage/replan.
7. **Activation journal-first**: persistir `activating` + candidate/base antes de mutar. Luego mover/aplicar exactamente el candidate commit por Git. Tras crash, recovery compara HEAD con base/candidate y reconcilia; no redispatch ciego.
8. **Post-activation probe** obligatorio. Si falla, rollback al base sólo cuando el journal demuestra que la transacción posee el cambio y no existe drift posterior; si no puede demostrarlo, `recovery_required`, nunca hard-reset ciego.
9. **Entrypoints canónicos**: `edit_own_file`, `pull_upstream`, `revert_last_edit` y `reset_to_upstream` deben atravesar la misma transaction authority o un adapter explícito equivalente. `exec`/`write_file` en local no pueden quedar como bypass de `RUNTIME_ROOT`: Policy debe detectar source-scope mutation y exigir la ruta transaccional, sin convertir shell general en allowlist cerrada.
10. **Rate guard unificado**: retirar la duplicación 10/20. La seguridad primaria es lease + isolation + verification + recovery. Cualquier frequency guard superviviente debe ser configurable/adaptativo y no bloquear recovery ni autorizar una mutación no verificable.
11. **No expansión lateral**: no crear capability registry, package manager authority, approval store, second Git authority ni second DB. P-013 sigue siendo dependencia de evidence fabric antes del cierre completo.

### Pre-mortem y failure matrix de implementación

- worktree creado pero process muere → journal + lease recovery retira/recupera workspace sin tocar active source;
- disk full/partial install/build timeout → candidate falla, active source permanece base;
- candidate verified pero active HEAD cambió → abort activation como stale base, no reset;
- process muere después de journal `activating` pero antes/durante Git effect → recovery compara HEAD base/candidate/other y reconcilia;
- post-probe falla → rollback sólo si ownership causal es demostrable;
- rollback falla → `recovery_required`, no success;
- segundo proceso intenta self-mod → lease conflict durable;
- schema migration incompatible → DB transaction rollback/fail closed antes de source activation;
- rate window stale/agotada durante recovery → recovery no depende del rate guard;
- >10 cambios pequeños legítimos → frequency alone no los vuelve peligrosos; cada activation sigue transaction gate;
- un solo cambio grande/no recuperable → se bloquea aunque contador esté vacío.

### Autonomía preservada / frontera deliberada de `exec`

- P-012 **no convierte self-modification en creator approval ni en una lista cerrada de cambios permitidos**. ABOS puede decidir y ejecutar sus propias correcciones; lo que cambia es que el source activo sólo recibe una versión después de candidate verification y activation causal.
- Se eliminó la falsa equivalencia “menos frecuencia = más seguridad”. Un cambio único no verificable sigue fallando; 10, 50 o más cambios válidos no se deniegan sólo por cantidad.
- El shell general permanece disponible fuera del active checkout. Inspección del repo dispone de `read_file`, `git_status`, `git_diff` y `git_log` sin pedir permiso humano.
- Un `exec` local que referencia el active checkout se intercepta porque un shell arbitrario ejecutado **directamente** sobre el source activo puede producir efectos antes de que ABOS tenga oportunidad de verificarlos. Eso es una frontera de activación, no una afirmación de que la operación sea ilegítima o imposible.
- No se implementó una blacklist/allowlist creciente de comandos. La evolución correcta, si una fase posterior necesita shell arbitrario sobre source como capability de primera clase, es **candidate-exec aislado** con equivalencia de path/cwd y evidencia, no volver a direct-write ni acumular prohibiciones por nombre de comando.
- Esta frontera queda clasificada como **capacidad redirigida / no pérdida de autonomía de self-mod**: edit/revert/reset/pull/write-to-runtime ya poseen camino transaccional. No se afirma que todo shell arbitrario multiarchivo sobre candidate esté implementado en P-012.
