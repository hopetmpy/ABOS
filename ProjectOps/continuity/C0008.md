### Reauditoría de autonomía antes de merge — defecto de over-protection

La revisión final sobre “inteligencia vs restricción” encontró una contradicción real antes de integrar P-012:

1. **HECHO — `PROTECTED_FILES` mezclaba fronteras reales con source evolutivo.** Inmovilizaba wallet/config/state/constitution y también piezas de software que ABOS necesita poder mejorar.
2. **HECHO — esa inmovilidad no era necesaria para evitar autodestrucción accidental.** La versión activa permanece intacta mientras el candidate vive aislado y pasa verification completa antes de activation.
3. **HECHO — código crítico ≠ código inmutable.** Transaction engine, Policy, tools y skills son de alto impacto, pero prohibir su evolución permanentemente sustituía juicio/verificación por rigidez.
4. **HECHO — existía un gap multiarchivo.** `package.json + pnpm-lock.yaml` no podía evolucionar coherentemente por cambios secuenciales single-file.
5. **DECISIÓN — frontera dura sólo para identidad/secrets/state/constitución y paths externos sensibles.** El source crítico es candidate-editable mediante gate completo.
6. **DECISIÓN — edición multiarchivo como una sola transacción.** Single-file conserva compatibilidad.
7. **DECISIÓN — no crear segunda tool/authority.** `edit_own_file` delega a la misma `editFiles()`.
8. **DECISIÓN — secrets/runtime state no se abren.** Son dominios de authority/state distintos.
9. **PARCIAL — `SOUL.md` requiere semántica específica de identidad/self-model.** Se preserva su authority hasta P-032 o auditoría explícita.
10. **NO HECHO — candidate-exec genérico.** Queda como ruta futura abierta; no se reintroduce shell directo sobre active source.

### Corrección final de autonomía — critical source evolutivo + multiarchivo

- `isProtectedFile()` conserva protección amplia para raw/direct writes sin candidate verification.
- `isImmutableFile()` separa credenciales/secrets, estado SQLite/config sensible, constitución y paths externos sensibles.
- `self-mod`, tools/router, Policy, skills y `package.json` pueden evolucionar mediante candidate aislado + full verification + activation causal.
- `editFiles()` añade una sola transacción multiarchivo; `editFile()` queda backward-compatible.
- `edit_own_file` acepta `path + content` o `edits=[{path,content}, ...]`; mezclar ambos se rechaza como intent ambiguo.
- Duplicate targets se rechazan antes de journal/lease; paths unchanged no abren cambio material.
- El threshold arbitrario de 100 KB fue retirado como falsa safety authority.
- Tests Git reales prueban activation atómica multiarchivo y que verification fallida no toca active source.
- `constitution.md` y demás fronteras realmente inmutables se rechazan antes de abrir una transacción.
