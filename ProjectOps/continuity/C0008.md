### Reauditoría de autonomía antes de merge — defecto de over-protection

La revisión final solicitada sobre “inteligencia vs restricción” encontró una contradicción real **antes de integrar P-012**:

1. **HECHO — `PROTECTED_FILES` mezcla fronteras reales con source evolutivo.** Actualmente inmoviliza no sólo wallet/config/state/constitution sino también `self-mod/code.ts`, transaction engine, repository operations, tools/router, PolicyEngine, skill loader/registry, `package.json`, `SOUL.md` y otras piezas que forman parte del software que ABOS debe poder mejorar.
2. **HECHO — esa inmovilidad no es necesaria para evitar autodestrucción accidental.** La versión activa de esas piezas permanece intacta mientras una nueva versión vive en worktree candidate. `verifyCandidateWorkspace()` ejecuta frozen install, typecheck, build y full tests antes de que el candidate pueda activarse; activation además conserva CAS/post-probe/rollback/recovery.
3. **HECHO — código crítico ≠ código inmutable.** Transaction engine, Policy, tools y skills son de alto impacto, pero prohibir su evolución permanentemente sustituye juicio/verificación por rigidez y contradice `Judgment before restriction`.
4. **HECHO — existe además un gap multiarchivo.** El runner ya soporta mutaciones multiarchivo, pero la superficie general `edit_own_file` expone un solo `{path, content}`. Así, incluso retirando `package.json` de la lista protegida, una modificación coherente `package.json + pnpm-lock.yaml` no puede pasar secuencialmente porque el primer candidate fallaría `--frozen-lockfile`.
5. **DECISIÓN — mantener como frontera dura sólo identidad/secrets/state/constitución y paths externos sensibles.** El source crítico debe ser candidate-editable y atravesar el gate completo; no direct-write.
6. **DECISIÓN — exponer edición multiarchivo como una sola transacción.** Mantener compatibilidad single-file; una request puede incluir varios archivos, todos se validan/stagean en el mismo candidate, se verifican juntos y se activan como un único commit causal.
7. **DECISIÓN — no crear una segunda tool/authority si no es necesaria.** Extender `edit_own_file` y hacer que single-file delegue al mismo `editFiles()` evita duplicación.
8. **DECISIÓN — no usar esta corrección para abrir secrets/runtime state.** Wallet, config, SQLite state, constitution y directorios sensibles siguen fuera de self-edit source ordinario porque son dominios de authority/state distintos, no porque el código sea “peligroso”.
9. **PARCIAL — `SOUL.md` requiere semántica específica de identidad/self-model.** No se abrirá por accidente en este cambio si existe una authority dedicada; debe preservarse la authority actual hasta P-032 o hasta auditoría explícita que demuestre que general self-edit es el productor correcto.
10. **NO HECHO — candidate-exec genérico.** No es requisito para corregir el over-protection inmediato. Se conserva como ruta futura abierta; no se reintroduce shell directo sobre active source.
