## Arquitectura implementada

### Coordinator y lifecycle

`src/capabilities/acquisition.ts` implementa:

`CapabilityRequest -> resolución inicial -> discovery -> candidate provenance/assessment -> route -> canonical registration/probe -> re-resolve del contrato original -> outcome`.

Propiedades verificadas:
- provenance + assessment explícitos antes de efectos externos;
- budget ceiling cuando existe coste conocido y rechazo honesto de coste no demostrable;
- deduplicación por route/candidate;
- no blind retry después de outcome incierto;
- registro sólo a través de P-014;
- éxito nominal de install/config/build nunca equivale a VERIFIED;
- `NO_DISCOVERED`, `UNKNOWN`, `UNAVAILABLE`, `UNAUTHORIZED`, `PROHIBITED`, `DEGRADED` y `VERIFIED` permanecen distintos;
- un candidato materialmente diferente puede seguirse tras rechazo de otro;
- Evidence Fabric recibe intentos/resultados sin convertirse en readiness authority.

### Runtime wiring

- `remediate_capability` permanece separado de `resolve_capability`.
- nested operations reingresan por `executeTool -> PolicyEngine` mediante `protected-tool-invoker`.
- dynamic/external tools no pueden shadowear silenciosamente nombres internos ABOS; duplicados ambiguos dentro de la misma trust class fallan cerrado.
- outer remediation persistence redacta nested probe/construction/composition values sensibles; los argumentos reales sólo llegan a la inner protected execution.

### MCP route

`src/capabilities/routes/mcp-functional-probe.ts` reutiliza P-015:
- sólo usa una capability MCP ya descubierta/proyectada;
- exige argumentos funcionales reales cuando son necesarios;
- ejecuta el tool MCP a través de su Policy boundary propia;
- re-resolve P-014 decide el resultado final;
- no inventa no-op arguments ni promoción por retorno nominal.

### Construction route

`src/capabilities/routes/p012-construction.ts` reutiliza P-012:
- source edits pasan por la authority transaccional existente;
- un transaction success sólo materializa estado adquirido/probe-pending en el proceso actual;
- source escrito no se promociona como capability usable sin reload/probe/evidence posterior.

### Composition lifecycle

`src/capabilities/routes/verified-composition.ts` + `src/capabilities/composition-tool.ts` implementan:
- plan declarativo durable sin runtime secret values;
- mínimo dos componentes y steps explícitos;
- sólo dependencies P-014 execution-ready;
- cada step debe estar cubierto por el contrato `provides` de los componentes declarados;
- functional probe y uso pasan por protected nested execution;
- persistencia del plan ligada a hash/version integrity;
- dependencia degradada o desaparecida degrada el composite;
- el executor vuelve a comprobar en cada ejecución que los contratos actuales de los mismos componentes todavía cubren cada `step.toolName`; contract drift no puede producir un silent provider/tool switch.
