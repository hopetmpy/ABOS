## Hallazgos verificables

1. `EnvironmentSelector` considera capability satisfecha mediante `available` y fuzzy text (`id`, `provider`, `description`, `requirements`).
2. P-014 considera `available:true` legacy sin state como `discovered_unverified`; no es execution-ready.
3. P-014 `capabilityProvides` usa channels contractuales normalizados (`provides`/`requirements`), no descripción libre.
4. `LocalEnvironmentProvider.canSatisfy`, `ConwayEnvironmentProvider.canSatisfy` y `AwsEnvironmentProvider.canSatisfy` reproducen matching boolean/textual y pueden afirmar satisfacción con descriptors no verificados.
5. `local:filesystem` se publica `available:true` sin state/evidence/authority, por lo que su significado P-014 actual es `discovered_unverified` aunque Local sí dispone de una base para verificar filesystem/proceso intrínseco.
6. Conway inspecciona credits y usa ese resultado para marcar `conway:sandbox`/`conway:inference` disponibles; credits/autenticación no prueban funcionalmente ambas capabilities.
7. AWS inspecciona CLI + STS y después marca EC2/SSM/Lambda/ECS/S3/SQS/DynamoDB/RDS disponibles; STS prueba identidad/control-plane auth, no acceso funcional a cada servicio.
8. `environment_capabilities` proyecta principalmente `available` y descripción/requisitos, perdiendo state/authority/evidence/provides para downstream.
9. Lifecycle/resource/mobility ya satisfacen la arquitectura provider-neutral esencial; duplicarlos sería regresión arquitectónica.
