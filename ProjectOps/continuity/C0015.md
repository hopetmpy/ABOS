## Consumer audit del fabric legacy — CERRADO

Hallazgos:
1. `ProviderRegistry`/`UnifiedInferenceClient` no son tests-only: `src/agent/loop.ts` los instancia en runtime.
2. `UnifiedInferenceClient` alimenta `createWorkerInferenceBridge()` y `Orchestrator`/planner.
3. `ProviderRegistry.resolveCandidates()` posee catálogo/tier/provider fallback independiente del `ModelRegistry`/`InferenceRouter` canónicos.
4. `UnifiedInferenceClient.chat()` agota retries de un provider y continúa silenciosamente al siguiente provider en errores retryable; tests legacy codifican expresamente ese comportamiento.
5. El main agent turn ya usa `InferenceRouter.route()` con `connectionProvider` explícito derivado de la conexión activa, por lo que existe una autoridad canónica disponible para reutilizar.
6. Workers exponen una interfaz pequeña `WorkerInferenceClient`; planner/plan-mode están acoplados por tipo concreto a `UnifiedInferenceClient`, no por necesidad funcional.
7. Con Codex como conexión activa, el legacy provider registry ni siquiera representa la misma connection/auth authority; conservarlo como runtime paralelo perpetuaría un split-brain de inferencia.

## Segunda unidad autorizada — canonical runtime migration

1. Introducir una interfaz estructural mínima para planner/orchestration inference en lugar de exigir la clase legacy concreta.
2. Implementar un adapter de orchestration/worker sobre `InferenceRouter` + el `InferenceClient` runtime existente; no crear otro registry/router/provider manager.
3. El adapter debe obtener `connectionProvider` desde la configuración viva y usar el mismo `ModelRegistry`, budget y evidence path que el main agent.
4. Mapear el intent legacy `reasoning|fast|cheap` a task intent/routing sin saltar policy/budget ni forzar provider/model externo a la conexión activa.
5. Migrar `agent/loop.ts` para workers + Orchestrator al adapter canónico y retirar del runtime principal la construcción de `ProviderRegistry`/`UnifiedInferenceClient`.
6. Mantener módulos legacy como compatibilidad mientras existan tests/API consumers externos; su retiro físico queda para P-035 salvo evidencia de no-consumer total.
7. Añadir regresiones que prueben: Codex/active connection se propaga, worker/planner no hace cross-provider fallback, dynamic catalog participa y P-013 cost/evidence sigue un solo path.
