## Findings verificables

### F1 — runtime principal usa stack cognitivo básico

`src/agent/loop.ts`:
- usa `MemoryRetriever` por turno;
- recupera los cinco tiers durables;
- formatea con `formatMemoryBlock()`;
- construye el prompt con `buildContextMessages()`;
- `ContextManager` y `EnhancedRetriever` no participan en el main turn path.

Existencia/test de módulos avanzados no equivale a runtime authority activa.

### F2 — `MemoryRetriever` NO es un duplicado prescindible

`src/memory/retrieval.ts` agrega, con budget, las authorities durables ya existentes:
- `working_memory`;
- `episodic_memory`;
- `semantic_memory`;
- `procedural_memory`;
- `relationship_memory`.

`EnhancedRetriever.retrieveScored()` no llama a `super.retrieve()` y sólo obtiene candidates desde `knowledge_store`. Reemplazar `MemoryRetriever` por `EnhancedRetriever.retrieveScored()` perdería los cinco tiers; H3 queda falsada como estrategia de reemplazo total.

### F3 — `ContextManager` ya preserva bundles de tool protocol

`src/memory/context-manager.ts` ya:
- tokeniza con BPE/fallback y cache acotado;
- recibe `modelContextWindow`;
- preserva system/todo/recent turns;
- renderiza cada `AgentTurn` como input → assistant/tool_calls → tool results;
- trunca tool results;
- aplica budget a task/memory/older turns/events;
- expone utilization y compactación.

Esto permite reutilizarlo como assembler del main path sin separar assistant tool_calls de sus resultados. El wiring deberá conservar además dos conductas del camino legacy que el manager aún no modela: pending input final y warning anti-repetition.

### F4 — `KnowledgeStore` es closed-world sólo en app/types

`src/memory/knowledge-store.ts` define `KnowledgeCategory` como cinco literals y `toKnowledgeEntry()` rechaza cualquier otro label.

`knowledge_store.category` en SQLite v10 es `TEXT NOT NULL`, sin CHECK enum. No se requiere migration para abrir categorías: la restricción es de aplicación.

### F5 — inferred category debe ser hint, no frontera de búsqueda

`EnhancedRetriever` infiere categorías conocidas y, cuando existen, las usa como filtro duro de `KnowledgeStore.search()`. Un label nuevo válido puede persistirse y quedar invisible aun cuando key/content coincidan con el query. La corrección debe buscar open-world y usar las categorías conocidas sólo como señal de ranking.

### F6 — feedback global es estado cross-agent accidental

`enhanced-retriever.ts` mantiene en módulo global:
- rolling precision window;
- feedback by turn;
- last rolling precision;
- una única `feedbackDb` reemplazada por cada constructor.

Dos loops/DBs en el mismo proceso pueden contaminar métricas y auto-match. Esa state no es durable cognitive authority; debe quedar instance-scoped. Reiniciar puede resetear la métrica sin perder conocimiento porque los stores durables son SQLite.

### F7 — persistence existente cubre la primera unidad sin crear otro store

- v5 ya posee working/episodic/semantic/procedural/relationship memory;
- v10 ya posee `knowledge_store` con category abierta a nivel durable, source, confidence, last_verified y expires_at;
- v18 Evidence Fabric ya posee correlation/causation, open `domain`/`authority_type`, `authority_id`, epistemic status y provenance JSON;
- P-013 conserva ownership de cross-domain causal/provenance evidence;
- `relationship_memory` conserva ownership de relaciones con entidades;
- P-022 posee la futura authority de World Model/beliefs.

Crear ahora un segundo graph/store de relaciones, facts o evidence duplicaría authorities existentes. No se abre schema v20 para la primera integración P-020. Si una prueba posterior demuestra una semántica durable imposible de representar sin falsedad, se reabre esa decisión con evidencia concreta.

### F8 — `event_stream` no se promueve automáticamente a context authority

`ContextManager` puede consumir events, pero los producers actuales no demuestran aún un único actor/identity contract para todo `event_stream` (por ejemplo, enhanced ingestion usa `sessionId` como `agentAddress`). P-020 no va a inyectar ese stream entero por mera disponibilidad. Evidence Fabric tampoco se convierte en prompt histórico masivo.

## Decisión técnica — DECISION_READY

Classification por pieza:

1. `MemoryRetriever`: **REUSE** como primitive de los cinco memory tiers.
2. `KnowledgeStore`: **CORRECT/EXTEND** para categorías open-world y stats dinámicos, sin migration.
3. `EnhancedRetriever`: **CORRECT/EXTEND** como activador/scorer suplementario de `knowledge_store`; category inference se vuelve hint, no filtro; feedback queda instance-scoped.
4. `ContextManager`: **REUSE/EXTEND** como assembler model-aware del main turn path; debe preservar pending input y anti-repetition sin romper tool protocol.
5. `buildContextMessages`: **REFACTOR/COMPATIBILITY**; conserva API legacy/tests donde existan, pero el main runtime deja de depender de él como authority de assembly una vez que `ContextManager` cubra su contrato material.
6. Persistence/schema: **NO_CHANGE** en esta unidad.
7. Evidence/relations/intelligence/skills: **REUSE**, sin absorber sus ownerships dentro de P-020.

Las incertidumbres restantes ya no cambian materialmente esta primera decisión ni exigen otra authority; el gate `DECISION_READY` queda satisfecho.

## Invariantes de implementación

1. Ningún wiring puede perder working/episodic/semantic/procedural/relationship memory.
2. Un category hint jamás puede ocultar un match open-world.
3. Tool call assistant message y tool result deben permanecer juntos y ordenados.
4. Pending input debe seguir siendo el último input del turno.
5. Anti-repetition debe conservarse como protección del loop.
6. Model context window se obtiene de ModelRegistry cuando exista; ausencia degrada a budget legacy, no a valor inventado.
7. Context/feedback in-memory puede reiniciarse; cognitive facts necesarios para recovery deben venir de SQLite.
8. No event/evidence dump masivo en prompt.
9. No nueva schema/migration salvo nueva evidencia discriminante.
