## Estado encontrado / último punto verificable

### F1 — ya existe un skill runtime real; no crear un segundo registry

`src/skills/registry.ts` ya puede:
- instalar skill desde Git;
- instalar skill desde URL;
- crear skill self-authored;
- persistirla vía `db.upsertSkill()`;
- deshabilitarla/removerla;
- listar skills.

`src/skills/loader.ts` ya revalida requisitos de bin/env en runtime/restart y `system-prompt.ts` inserta instrucciones activas bajo trust boundary UNTRUSTED.

Por tanto P-021 no debe crear otro loader/install path ni saltarse el tool/policy path existente.

### F2 — la persistence actual destruye historia de versión

La tabla `skills` posee `name` como PRIMARY KEY y `upsertSkill()` usa `INSERT OR REPLACE`. Un update reemplaza el snapshot previo; no existe historial durable de versiones, provenance por versión, validation state ni rollback target.

Esta brecha es material respecto al DoD de P-021. `NO_CHANGE` queda provisionalmente falsada.

### F3 — procedural memory ya posee aprendizaje procedural durable

`src/memory/procedural.ts` mantiene procedimientos por nombre con steps, success/failure counts y last-used. Es una primitive de aprendizaje que debe REUSE; convertirla en un segundo skill registry duplicaría responsabilidades.

Skill y procedural memory no son equivalentes:
- procedural memory = conocimiento de cómo;
- skill = artefacto/instrucción reusable, activable y gobernada por requisitos/version/lifecycle.

### F4 — Capability Fabric ya posee la authority de execution readiness

`CapabilityRegistry.ingestSkills()` proyecta inventario de skills como capabilities `skill:<name>`.

Importante:
- enabled inventory => `discovered_unverified`, no `verified_available`;
- inventory por sí sola NO demuestra readiness;
- `CapabilityResolver` sólo permite `use_existing` cuando capability + dependencies + contract están `verified_available`.

P-021 debe registrar evidence-backed validation en Capability Fabric; no debe inventar un booleano paralelo de “skill usable”.

### F5 — capability contract ya soporta piezas que P-021 necesita

`CapabilityDescriptor` ya admite:
- open type/state;
- provides;
- permissions;
- effects;
- dependencies;
- version;
- compatibility;
- environment;
- inputs/outputs;
- estimated cost;
- evidence + authority + observedAt.

No se crea otra contract taxonomy para skills salvo metadata específica realmente ausente.

### F6 — Evidence Fabric ya es la authority de provenance/correlation

P-013 `appendEvidenceEvent()` soporta domain/authority type/id abiertos, correlation/causation, epistemic status, payload/provenance con redaction y consultas por authority.

Skill evolution debe emitir/correlacionar evidence aquí, pero el estado de versión seguirá perteneciendo a la authority durable de skill lifecycle; Evidence Fabric no se convierte en source of truth del lifecycle.

### F7 — policy/tool path ya gobierna creación/instalación

`install_skill`/self-create existen como tools y pasan por la misma ejecución/policy authority de herramientas. P-021 no debe añadir una ruta oculta que eleve permisos o esconda effects/tools subyacentes.

### F8 — tests actuales protegen runtime truth y trust boundary

- persisted enabled skill no se reactiva tras restart si falta un requisito runtime;
- se reactiva cuando requisito vuelve a existir;
- path/YAML/injection/size/trust hardening ya están cubiertos.

Estos tests son baseline de regresión, no evidencia suficiente de evolution/versioning.

## Riesgo / invariantes

1. Una skill candidate no se promueve sólo por existir o por una ejecución aislada.
2. Skill no puede elevar permisos ni ocultar tools/effects/capabilities requeridas.
3. Inventory/enabled no equivale a execution-ready.
4. Versiones y rollback deben sobrevivir restart.
5. Failure debe degradar applicability/evidence, no borrar historia.
6. Secrets/tokens/credentials no deben materializarse dentro de skill provenance/content.
7. No segunda source of truth para capability readiness, procedural learning, policy o evidence.
8. Update/rollback de skill debe ser transaccional respecto a la proyección runtime para no dejar active version parcialmente cambiada.
9. No introducir thresholds arbitrarios sin evidencia/semántica del plan.
