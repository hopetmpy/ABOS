## Findings finales de auditoría

### F1 — skill runtime existente se reutiliza

Registry/loader/format, tool/policy path e injection/runtime-requirement hardening ya existen. Crear otro loader/registry sería authority paralela.

### F2 — `skills` actual es snapshot runtime, no version authority

`skills(name PRIMARY KEY)` + `INSERT OR REPLACE` destruye snapshots previos. No conserva parent version, lifecycle, validation, provenance por versión ni rollback target.

### F3 — stores existentes NO son equivalentes a skill version history

- `modifications`: audit log genérico con description/file/diff opcional; no posee definición completa/version/lifecycle/active selection.
- self-mod journal P-012: gobierna transacciones de source/base SHA; no es authority de skill state y no cubre skills instaladas como runtime state.
- Evidence Fabric: por definición es correlation/provenance cross-domain y explícitamente no reemplaza domain authorities.
- procedural memory: procedure/steps/outcome counts, pero no distribución/activation/versioning de SKILL runtime.

H4 queda confirmada: se requiere persistence aditiva específica de skill versions/evaluations.

### F4 — `skills` puede seguir como proyección runtime compatible

Los consumers existentes leen `skills` para loader/system prompt. No hace falta migrarlos a una segunda API destructivamente. La nueva authority de version lifecycle seleccionará una versión y proyectará su definición a `skills`; history seguirá append-oriented en las nuevas tablas.

### F5 — Capability Fabric ya es la única authority de execution readiness

`CapabilityRegistry`:
- trata inventory enabled como `discovered_unverified`;
- sólo `verified_available` + dependency chain permite execution-ready;
- exige authority/evidence/observedAt para un verified claim;
- fingerprints incluyen `version`, dependencies, effects, compatibility, I/O.

P-021 no tendrá un booleano paralelo de readiness. La definición de skill version se proyectará a `CapabilityDescriptor`; promotion evidence se registrará con `recordProbe()`.

### F6 — definición actual de skill no participa suficientemente en fingerprint

`ingestSkills()` sólo proyecta name/description/enabled; instructions/required capabilities/version no cambian hoy la capability definition fingerprint. P-021 debe enriquecer el descriptor de skills evolucionadas con version/dependencies/contracts para que cambiar una versión invalide evidence obsoleta en lugar de heredarla accidentalmente.

### F7 — prompt runtime debe reaccionar a lifecycle sin restart

El `skills` array usado por `buildSystemPrompt()` puede quedar estático durante un proceso. P-021 debe refrescar inventory activa desde DB por turno y, para skills gestionadas por evolution, inyectar instrucciones sólo cuando la capability `skill:<name>` siga execution-ready. Legacy skills no gestionadas conservan compatibilidad actual.

### F8 — filesystem no puede volver a ser authority sobre una skill gestionada

`loadSkills()` reparsea `SKILL.md` y actualmente refresca `skills`. Para una skill gestionada por version lifecycle, esa ruta podría sobrescribir la proyección activa tras restart. La loader/registry legacy debe detectar skill gestionada y no sobrescribir/dehabilitar lifecycle fuera de la nueva authority. El DB version store será canónico; `skills` será projection.

### F9 — promotion no puede basarse en autoevaluación desnuda

Evaluation debe referenciar evidence real existente. El engine no aceptará un string “success” sin un evidence event durable. Promotion contará success observations por evidence IDs distintos. Verification policy será explícita por candidate; para critical skills una sola evidencia jamás satisface el gate (floor semántico = dos observaciones independientes, derivado directamente del invariante del plan, no de un scoring arbitrario).

## Arquitectura decidida

### A. Persistence additive v20

Crear:
- `skill_versions`: definición completa immutable-per-version, parent, lifecycle, contract/applicability/verification policy, content hash, provenance/evidence y timestamps;
- `skill_evaluations`: observations append-only de replay/validation/usage con outcome y referencia a evidence real.

No se elimina `skills`; permanece current runtime projection por compatibilidad.

### B. SkillEvolutionStore / SkillEvolutionEngine

Operaciones canónicas:
- create candidate / evolve candidate;
- record evidence-backed evaluation;
- assess promotion;
- activate validated version;
- degrade/deprecate without erasing history;
- rollback to a previously validated version;
- list/history/restart recovery.

Projection a `skills` se actualiza transaccionalmente junto con lifecycle DB state. Filesystem legacy no podrá sobrescribir una skill marcada managed.

### C. Capability integration

La active/version candidate declara:
- required capabilities;
- provides;
- permissions/effects;
- environment/compatibility;
- inputs/outputs;
- version.

`CapabilityRegistry` sigue siendo readiness authority. Promotion exige dependencies execution-ready y successful validation evidence; `recordProbe()` materializa el verified claim. Definition fingerprint cambia por versión/contract.

### D. Evidence + procedural reuse

- Evidence Fabric correlaciona candidate/evaluation/activation/degrade/rollback usando `authorityType=skill_version`.
- Procedural memory puede originar/señalar candidates y aportar usage history, pero no promueve por sí sola ni se vuelve skill registry.
- evidence IDs se validan contra Evidence Fabric; no se acepta provenance inventada.

### E. Runtime/tools

Agregar tools explícitas de lifecycle que siguen PolicyEngine normal: propose/evaluate/activate/degrade/rollback/list. No ruta oculta ni elevación de permisos.

Main loop refresca skill inventory desde DB y filtra evolved skill prompt activation por Capability Fabric. Legacy skills fuera de evolution conservan semántica compatible.

## Riesgo / invariantes de implementación

1. candidate != active != verified capability.
2. un success aislado no promociona critical skill.
3. skill no eleva permisos ni oculta dependencies/effects.
4. version history y rollback sobreviven restart.
5. failure/degrade no borra history.
6. secrets no se persisten como skill/provenance; inputs sospechosos se rechazan y Evidence Fabric redaction sigue aplicando a evidence.
7. no segunda authority para capability readiness/procedural/policy/evidence.
8. current projection + lifecycle se actualizan en una transacción SQLite; crash no deja dos active versions.
9. cambio de definition/version invalida capability evidence anterior por fingerprint.
10. loader/registry legacy no sobrescriben managed skill authority.
11. Unknown/unavailable dependency no se convierte en success falso.
