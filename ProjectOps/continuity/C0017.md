## F9 — repeated P-016 Windows/Node 22 readiness false-negative blocks exact-main closure

### Observaciones

1. En un head P-021 anterior (`4947ef8...`), Windows/Node 22 falló en el primer test `executes with explicit confined cwd and env` porque `LocalComputerRuntime.requireShell()` recibió `probe.available=false`; el test inmediatamente posterior que usa el mismo Git Bash + Job Object provider pasó. Un rerun dirigido quedó verde.
2. En el exact-main merge `c36c97d...`, ProjectOps `35948816442` es SUCCESS y siete lanes CI son SUCCESS; sólo `windows-regression (22)` del CI `35948816508` vuelve a fallar en exactamente el mismo primer test P-016.
3. En ese job, checkout/install/typecheck/build/smoke Windows pasan. El primer P-016 test tarda ~30.5 s y falla en `requireShell`; el test posterior `probes the same canonical Git runtime shell through Job Object ownership` pasa en ~0.68 s, y otros process lifecycle tests también pasan.
4. `src/platform/windows-job-process.ts` crea un PowerShell nuevo y compila el owner C# mediante `Add-Type` antes de ejecutar el shell. `runWindowsJobProcessSync()` usa `commandTimeout + WINDOWS_JOB_BOOTSTRAP_GRACE_MS`; actualmente el probe aporta 5 s y el bootstrap grace es 20 s, por lo que el provider puede ser asesinado alrededor de 25 s antes de completar un cold bootstrap bajo carga.
5. `LocalComputerRuntime.probe()` cachea hoy tanto positives como negatives. Por ello un timeout transitorio de bootstrap puede convertirse en indisponibilidad persistente para esa instancia de runtime hasta restart.
6. El provider P-016 y su test no fueron modificados por P-021; `windows-job-process.ts` proviene del merge P-016 `08b7a5cce8f18c57c52e6a2f43048b6f1c214e50`.

### Hipótesis discriminadas

- H1 — Git Bash / Job Object realmente no disponible en Windows Node 22: FALSADA. El mismo job demuestra el provider operacional inmediatamente después; Windows Node 24 y múltiples runs Node 22 también pasan.
- H2 — regresión source causada por P-021: FALSADA. P-021 no cambió la authority P-016 y el mismo source alterna PASS/FAIL según cold bootstrap.
- H3 — cold bootstrap del PowerShell `Add-Type` excede el presupuesto de provider y produce false-negative: SOPORTADA FUERTEMENTE por repetición, duración del primer test, timeout efectivo y éxito inmediato posterior.
- H4 — es sólo flake de test sin efecto productivo: FALSADA. `exec()` y `start()` pasan por `requireShell()`/`probe()`, y el negative probe queda cacheado en product runtime.
- H5 — ampliar sólo el timeout del test: RECHAZADA; ocultaría un false-negative real del runtime.

### Decisión

`DECISION_READY` para `CORRECT` dentro de authorities P-016 existentes, sin reabrir arquitectura ni crear provider paralelo:

1. aumentar el presupuesto de **bootstrap del provider** de forma separada al timeout del comando para tolerar cold `Add-Type` en hosts Windows lentos/cargados;
2. usar el mismo presupuesto de bootstrap para la readiness async del Job Object owner;
3. mantener fail-closed para shell inexistente, provider error duro o command failure;
4. no cachear un `providerTimedOut` como indisponibilidad permanente: una operación posterior puede volver a probar; no se convierte UNKNOWN/transient en false estable;
5. añadir regresión Windows determinista para la semántica non-sticky del timeout, además de exigir el Windows CI real;
6. no alterar P-016 plan: objetivo, architecture, authorities, dependencies y DoD siguen vigentes; se corrige un defecto de implementación descubierto por exact-main validation de P-021.
