## F11 — discriminación exacta del fallo Windows / DECISION_READY

### Evidencia nueva

Los logs exactos del CI `35949853711` falsaron que la nueva regresión de `providerTimedOut` fuera el fallo actual:
- Windows Node 22 y Node 24 fallaron en el mismo test existente: `P016 local computer runtime > executes with explicit confined cwd and env`;
- el motivo exacto fue `Test timed out in 30000ms`;
- `p016-windows-probe-stability.test.ts` sí pasó en ambos lanes;
- no apareció un assertion failure que demostrara cwd/env incorrectos, false readiness o pérdida de Job ownership.

La revalidación sobre el `main` más reciente `206cf74d...`, CI `35952635313`, agregó evidencia discriminante:
- existe un único workflow `CI`; ProjectOps verification corre dentro de `build-and-test` y pasa;
- Windows Node 22 pasó;
- Windows Node 24 volvió a fallar en el mismo test por timeout de 30 s;
- los demás lanes permanecieron verdes.

El cierre original P-016 aporta control histórico válido: exact-main CI `35809162263` pasó 8/8 y ese mismo test se ejecutó en Windows Node 24 en ~19.3 s sobre la misma generación de runner. Por tanto, el test sí cubría la ruta real, pero su wall-clock varía materialmente.

Source/authority reconstruidos:
- `LocalComputerRuntime.exec()` llama `requireShell()`; el primer uso de una instancia Windows ejecuta el probe de readiness y lo cachea;
- el probe Windows usa command budget de 5 s más bootstrap grace del provider;
- después `exec(..., 10_000)` ejecuta una segunda invocación provider-bound para el comando real;
- el diseño P-016 aceptado exige readiness real cacheada por runtime y explícitamente no define SLA de startup;
- la authority histórica P-016 rechazó ampliar timeouts/retries como sustituto de ownership correctness.

Con el baseline aceptado de bootstrap grace 20 s, el primer test puede consumir un camino válido acotado cercano a 25 s de readiness + 30 s del exec antes de overhead, mientras Vitest aborta el test completo a 30 s. El gate tiene por tanto un presupuesto menor que la semántica que pretende verificar.

### Hipótesis discriminadas

- H0 `WINDOWS_TEST_GATE_BUDGET_MISMATCH`: **CONFIRMADA** por source, budgets explícitos, histórico ~19.3 s, fallos 30 s variables y main Node22 PASS / Node24 FAIL.
- H1 `TRANSIENT_PROVIDER_TIMEOUT_STICKINESS_IS_CURRENT_FAILURE`: **FALSADA para el fallo actual**. La regresión non-sticky pasa; no obstante, cachear un timeout transitorio como indisponibilidad permanente sigue siendo un defecto semántico separado y la hardening se conserva.
- H2 `INCREASE_PRODUCT_BOOTSTRAP_TO_60S`: **FALSADA / REJECTED**. La rama siguió roja y el cambio amplía un budget de producto sin resolver el gate; no existe evidencia para cambiar el baseline aceptado de P-016.
- H3 `REMOVE_OR_BYPASS_READINESS_PROBE`: **REJECTED**. Contradice la authority P-016 de evidence-backed readiness y no es necesario para explicar los fallos.
- H4 `RUNNER_IMAGE_REGRESSION`: **FALSADA como causa suficiente**. El mismo runner generation produjo ejecuciones verdes y rojas; la evidencia soporta sensibilidad de timing/carga, no una ruptura semántica demostrada.

### Decisión

`DECISION_READY`: `CORRECT_TEST_GATE / RETAIN_TRANSIENT_PROBE_HARDENING / REVERT_UNJUSTIFIED_BOOTSTRAP_EXTENSION / NO_ARCHITECTURE_CHANGE`.

Corrección autorizada:
1. restaurar el bootstrap grace del Windows Job provider al baseline P-016 aceptado de 20 s;
2. conservar la semántica non-sticky para `providerTimedOut` y su regresión;
3. aislar las regresiones P-016 de proceso Windows en un paso CI propio con timeout de test explícito y derivado de los budgets del runtime, sin ampliar el timeout de las demás pruebas;
