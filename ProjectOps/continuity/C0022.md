## Objetivo

Maximizar resultado útil por recurso cognitivo gastado, no simplemente minimizar tokens. Antes de inferencia, ABOS debe poder considerar memoria/cache, retrieval/context activation, cálculo/código/tool, skill/procedure, simulation/replay e inferencia; cuando requiera modelo debe elegir contexto/model/reasoning de forma compatible con autoridad, provider boundary, model lock y budgets existentes.

La optimización no puede degradar silenciosamente success/quality. El coste material debe incluir cuando aplique tokens, latencia, dinero, contexto, retry/rework y evidencia de outcome; reusable learning creado forma parte del valor, no sólo del gasto.

## Decisión — DECISION_READY

Classification: `CREATE_NARROW_CONTROLLER + REUSE_EXISTING_EVIDENCE/AUTHORITIES`.

El controller autorizado es únicamente una authority de decisión/orquestación: compara candidates existentes, preserva UNKNOWN y quality evidence, registra rationale/execution/outcome en Evidence Fabric y delega. No es executor, model/provider router, inference ledger, memory/skill/simulation owner ni database owner.

Una alternativa más barata sólo puede desplazar baseline con evidencia de outcome/quality suficiente y recursos comparables; UNKNOWN no equivale a cero ni a éxito. Savings materiales requieren baseline comparable + coste observado + quality-valided success.

## Implementación material

### Controller estrecho

Se creó `src/intelligence/cognitive-cost-controller.ts`.

Responsabilidades implementadas:
- candidates `memory | deterministic | skill | simulation | inference`;
- availability `available | unavailable | unknown`;
- comparación de coste, latencia, contexto y retry/rework cuando existen datos;
- information gain, uncertainty, reversibility y reusable learning como evidencia/metadata sin apropiarse de sus authorities;
- receipts `cognitive.route_selected`, `cognitive.route_executed`, `cognitive.outcome_recorded` en Evidence Fabric;
- reconstrucción restart-safe de estadísticas desde `evidence_events`;
- lectura de estimaciones de inferencia desde `inference_costs`, sin segundo ledger;
- execution/outcome idempotentes por decisión;
- material savings sólo para success quality-validado con baseline/actual comparables.

Adversarial correction: la primera versión contenía defaults numéricos de quality/min samples no autorizados por ninguna authority. Se eliminaron. El controller no impone un quality threshold global; un dominio puede suministrarlo explícitamente. Sin threshold de dominio, el downgrade exige outcome validado, ausencia de validated failure/rework y no empeorar quality comparable.

### Orchestration inference tiers

`src/inference/router-orchestration-client.ts` ahora puede adaptar `reasoning | fast | cheap` por evidencia de outcome/recursos antes de delegar. `InferenceRouter` sigue siendo el único owner de provider/model/model lock/fallback/budgets.

Compatibilidad adversarial: embeddings/tests legacy que inyectan un router con `route()` pero sin `selectModel()` no se rompen; challenger availability queda UNKNOWN y el requested baseline se preserva.

Un API response exitoso NO se registra como quality success. La calidad de planificación sólo se valida en el quality gate downstream de strategic review.

### Strategic model/no-model boundary

`src/orchestration/orchestrator.ts` registra causalmente:
- existing materialized Task graph → ruta determinista/no-model, cost/latency/context 0, quality-valided reuse;
- new top-level Goal → requiere strategic planning; provider/model final sigue sujeto al router;
- strategic review aprobado → outcome quality-validado para la cognitive decision que produjo el plan;
- strategic review no aprobado → rework registrado sin fabricar causalidad de model-quality failure.

### Main ReAct turn

Se creó `src/agent/cognitive-preflight.ts` y se integró en `src/agent/loop.ts`.

Antes de `InferenceRouter.route()` el loop ahora considera explícitamente candidates de inference, memory, skill, deterministic/tool y simulation y deja receipt causal. Para evitar falsos no-model claims:
- memoria/knowledge recuperada = `UNKNOWN` como direct answer porque su contrato actual enriquece contexto;
- skills prompt-eligible = `UNKNOWN` como direct execution si no hay binding directo validado;
- tools disponibles = `UNKNOWN` si aún no existe route/arguments task-specific;
- simulation = no direct route sin un resultado task-bound;
- inference current tier = baseline verificable y luego el router conserva su authority.

El main turn registra execution actual desde el router y un outcome no-quality-validado tras persistir el turno. Tool errors/rework se conservan, pero completion por sí sola no se convierte en quality success.
