## Objetivo

Extender la authority existente de actor selection para que ABOS pueda seleccionar ejecución local, agent/worker/child u otro actor elegible según task requirements, verified capabilities, experiencia/outcome evidence contextual, availability/health, environment access, coste/latency, trust/authority y constraints, sin duplicar Capability, Environment, Evidence, Policy, lifecycle ni Task authority.

## Invariantes

- no convertir roles/departments en taxonomy cerrada ni authority de competencia;
- parent y child conservan authority propia; no se prestan permisos por selección;
- UNKNOWN no equivale a false, cero coste ni incapacidad;
- historical performance se interpreta por task class/contexto, no como reputación global rígida;
- coste esperado debe considerar inference/environment/coordination cuando exista evidencia; ausencia no equivale a cero;
- availability/health/environment stale no se trata como readiness actual;
- registration order o “primer idle” no puede ser el criterio material de selección;
- delegation puede seleccionar ejecución local si es la alternativa justificable;
- failure/reassignment actualiza evidence; no etiqueta incapacidad permanente;
- no crear segunda Capability, Environment, World Model, Evidence, Cognitive Cost, Policy/Authority, child lifecycle o task authority.

## Hipótesis discriminadas

### H0 — `NO_CHANGE` — FALSADA

`Orchestrator.matchTaskToAgent()` selecciona hoy por `agentRole`, primer idle compatible con environment, `getBestForTask(role)` y finalmente spawn/busy/self fallback. `SimpleAgentTracker.getBestForTask()` devuelve literalmente el primer idle. No compone competence/outcome/cost/authority y el orden de registro puede decidir materialmente.

### H1 — `EXTEND_EXISTING_DELEGATION_SELECTOR` — CONFIRMADA

Existe un único owner material de actor selection: `Orchestrator.matchTaskToAgent()`. La intervención debe conservar ese boundary y sustituir su criterio rígido por un matcher evidence-driven, no crear un segundo orchestrator.

### H2 — `CREATE_NARROW_COMPETENCE_MATCHER_OVER_EXISTING_AUTHORITIES` — CONFIRMADA COMO IMPLEMENTACIÓN INTERNA DE H1

El matcher puede ser un componente estrecho dentro de `src/orchestration/` que componga authorities existentes. No será nueva source of truth ni persistirá un profile paralelo.

### H3 — `UNIFY_PARALLEL_DELEGATION_PATHS` — FALSADA

`EnvironmentSelector`/`EnvironmentExecutionBridge` seleccionan environment/executor para spawn/mobility y no compiten con actor selection. Colony/local/AWS son adapters de ejecución/transport bajo la misma Task authority; no son selectores paralelos de actor semánticamente equivalentes.

### H4 — `REFACTOR_TASK_REQUIREMENTS_OR_ACTOR_PROFILE_CONTRACT` — PARCIALMENTE CONFIRMADA

`TaskNode` ya expresa `requiredCapabilities`, `preferredEnvironment`, coste estimado, timeout y strategic path mediante el binding adaptativo. El gap contractual está del lado actor: `AgentTracker` sólo expone idle/name/role/status y `getBestForTask(role)`. El matcher debe derivar profile actual desde authorities existentes en vez de crear una tabla de competence.

## Evidencia del audit

- `src/orchestration/orchestrator-core.ts`: actor selection actual = direct role match → `getBestForTask()` → spawn → busy reassign → self fallback.
- `src/orchestration/simple-tracker.ts`: `getBestForTask()` retorna `getIdle()[0]`; no hay scoring de competencia.
- `src/orchestration/task-graph.ts` + `adaptive_task_bindings`: la Task ya conserva requirements y execution intent; no hace falta otro Task contract.
- `src/environments/selector.ts`: environment selection ya posee capability-fit, availability, reliability, cost, reuse y policy; UNKNOWN se conserva. No se duplicará.
- `src/environments/task-executor.ts` + `src/environments/mobility.ts`: spawn/dispatch y provider mobility ya son authorities canónicas y preservan evidence/recovery.
- `src/environments/resource-store.ts`: `environment_resources` ya conserva actor-linked resources, capabilities, environment, estimated/actual cost, health/status y evidence.
- `src/agent/loop.ts`: `resolveExecutionEnvironment()` y `isWorkerAlive()` ya proyectan environment ownership/health; dispatch mantiene authority del actor concreto.
- `src/orchestration/colony-task-assignment.ts`: child sólo acepta Task del parent configurado y la respuesta sólo se acepta del actor asignado; selection no debe prestar authority.
- `task_graph.result`, `actual_cost_cents`, `assigned_to` y `adaptive_task_bindings` permiten derivar outcome/cost history por actor y task context sin una reputación global nueva.
- Capability Fabric permanece authority para parent/local capabilities; child competence sólo puede promoverse desde evidence ligada al child/resource, no desde las capabilities del parent.

## Decisión

Implementar `EXTEND + NARROW_MATCHER` dentro de orchestration:

1. `Orchestrator.matchTaskToAgent()` seguirá siendo el único owner de la decisión.
2. Un matcher evidence-driven derivará candidates actuales (idle children/workers + parent/local candidate cuando sea elegible) sin usar registration order como ranking.
3. Capability evidence será positiva y actor-specific: capabilities ligadas a resources del actor y, para parent/local, Capability Fabric actual. Ausencia de evidence será UNKNOWN, no incapacidad.
4. Historical outcome/cost/latency se derivará de Task history contextualizada por requirements/task class; no se persistirá reputación global rígida.
5. Environment/health/authority se reutilizarán desde callbacks/resources actuales; actor no observable o environment incompatible no se presentará como ready.
6. Spawn seguirá delegado a Environment Mobility cuando no exista actor existente suficientemente justificable; su environment selector conserva su authority.
7. Se retirará `busy-agent reassign` como criterio ordinario de selección: busy no equivale a available y puede provocar doble asignación.
8. Cada selección persistirá un receipt explicable en Evidence Fabric con requirements, candidates, known/unknown evidence, coste/latency conocidos y reason; Evidence Fabric no se convierte en Task authority.
9. Failure posterior alimentará la misma historia de Tasks; el siguiente selection recalculará desde evidence actual, sin etiqueta permanente.

## Adversarial targets antes de aceptar

- dos idle en distinto orden deben producir la misma selección;
- verified capability debe superar role-only cuando requirements materiales existen;
- new/unknown actor sigue elegible si no hay evidence negativa, pero no se promociona por default inventado;
- stale/dead/unavailable actor no puede ganar;
- preferred environment es constraint material;
- high-cost specialist puede perder frente a actor de competencia/outcome equivalente y menor coste conocido;
- failure + retry/reassignment reevalúa history y no repite ciegamente al mismo actor;
- restart reconstruye decisión desde DB/resources/evidence sin cache en memoria;
- parent capability no se presta a child;
- local parent puede ganar como candidate normal, no sólo fallback silencioso;
- spawn conserva EnvironmentSelector/Mobility como authority y no se duplica su scoring.
