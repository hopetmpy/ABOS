## Auditoría causal — hallazgos materiales

### Birth / constitution

1. `src/replication/constitution.ts` ya posee `propagateConstitution()` y `verifyConstitution()` con SHA-256. **REUSE/CORRECT**, no reemplazar.
2. `spawnChild()` y el legacy path envuelven `propagateConstitution()` en `catch {}` y continúan. Cualquier falta local, fallo de escritura, fallo de hash persistence o error de transporte queda degradado a best-effort.
3. El lifecycle pasa `sandbox_created -> runtime_ready -> wallet_verified` sin ejecutar `verifyConstitution()` como gate causal.
4. `ensureChildRuntimeRunning()` puede promover `funded -> starting -> healthy`, o reconciliar `unhealthy -> healthy`, sólo por observar el proceso `node dist/index.js --run`; no revalida constitution/bootstrap antes de marcar healthy.
5. `ChildHealthMonitor` clasifica health por presencia de proceso child-scoped. Esto es buena autoridad de **process liveness**, pero no prueba birth/bootstrap integrity.
6. El test vigente de `ensureChildRuntimeRunning()` construye manualmente `funded` sin bootstrap attestation y espera `healthy`; por tanto la suite actual codifica la semántica incompleta que P-029 debe invertir.
7. Los tests de spawn mockean lectura local de constitution como fallo y aun esperan spawn exitoso; también codifican el best-effort histórico.

### Identity / wallet / genesis / lineage

1. `genesis.json` se materializa antes de `--init`; `bootstrapFromGenesisIfPresent()` reutiliza config, wallet, heartbeat, SOUL y skill helpers canónicos y persiste `parentAddress` en child config. **REUSE/EXTEND**.
2. `--init` crea/obtiene wallet soberano del child y el parent sólo acepta una address parseada/validada antes de `wallet_verified`. No hay evidencia de préstamo de parent wallet.
3. Parent lineage durable ya vive en `children` + `child_lifecycle_events`; child lineage vive en config/genesis `parentAddress`. No crear otra lineage authority.
4. Reused sandbox conserva `/root/.abos` fuera de `/root/abos`; cualquier bootstrap nuevo debe ser idempotente y sobrescribir/validar artefactos con lineage actual para impedir stale state.

### Family Knowledge / skills / capabilities

1. `KnowledgeStore` ya es la authority durable del `knowledge_store`; `EnhancedRetriever` ya la consume en retrieval normal. **EXTEND**, no segundo memory store.
2. `knowledge_store.source` es string durable y puede transportar provenance familiar sin migration si se usa un formato explícito/versionado.
3. La memoria episódica/working/semantic cruda es separada y no debe copiarse wholesale. La proyección familiar debe partir del store curado y/o de catálogos, no de episodic history.
4. Skills ya poseen registry durable. Heredar catálogo no significa instalar/copiar instrucciones arbitrarias; el catálogo familiar es conocimiento/provenance.
5. CapabilityRegistry/CapabilityStore ya distinguen inventory de `verified_available` y exigen authority/evidence/observedAt. Una capability verificada en parent **no** puede convertirse en execution-ready del child sólo por herencia. El child puede heredar el catálogo como conocimiento, preservando state/evidence, sin registrarlo como capability propia.
6. No existe una proyección familiar que una KnowledgeStore + skill catalog + capability catalog con lineage/provenance. Ese delta justifica el adapter estrecho de H4.

## Decisión DECISION_READY

Clasificación material:

- Constitution helpers: `REUSE + CORRECT WIRING`.
