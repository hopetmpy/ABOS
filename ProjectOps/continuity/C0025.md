## Auditoría causal — hallazgos materiales

### Birth / constitution

1. `src/replication/constitution.ts` ya posee `propagateConstitution()` y `verifyConstitution()` con SHA-256. **REUSE/CORRECT**, no reemplazar.
2. `spawnChild()` y el legacy path envolvían `propagateConstitution()` en `catch {}` y continuaban. Cualquier falta local, fallo de escritura, fallo de hash persistence o error de transporte quedaba degradado a best-effort.
3. El lifecycle pasaba `sandbox_created -> runtime_ready -> wallet_verified` sin ejecutar `verifyConstitution()` como gate causal.
4. `ensureChildRuntimeRunning()` podía promover `funded -> starting -> healthy`, o reconciliar `unhealthy -> healthy`, sólo por observar el proceso `node dist/index.js --run`; no revalidaba constitution/bootstrap antes de marcar healthy.
5. `ChildHealthMonitor` clasificaba health por presencia de proceso child-scoped. Esto es buena authority de **process liveness**, pero no prueba birth/bootstrap integrity.
6. El test anterior de `ensureChildRuntimeRunning()` construía manualmente `funded` sin bootstrap attestation y esperaba `healthy`; por tanto la suite codificaba la semántica incompleta que P-029 debía invertir.
7. Los tests de spawn mockeaban lectura local de constitution como fallo y aun esperaban spawn exitoso; también codificaban el best-effort histórico.

### Identity / wallet / genesis / lineage

1. `genesis.json` se materializa antes de `--init`; `bootstrapFromGenesisIfPresent()` reutiliza config, wallet, heartbeat, SOUL y skill helpers canónicos y persiste `parentAddress` en child config. **REUSE/EXTEND**.
2. `--init` crea/obtiene wallet soberano del child y el parent sólo acepta una address parseada/validada antes de `wallet_verified`. No hay evidencia de préstamo de parent wallet.
3. Parent lineage durable ya vive en `children` + `child_lifecycle_events`; child lineage vive en config/genesis `parentAddress`. No crear otra lineage authority.
4. Reused sandbox conserva `/root/.abos` fuera de `/root/abos`; P-029 resetea estado bootstrap stale antes de reasignar lineage/wallet.

### Family Knowledge / skills / capabilities

1. `KnowledgeStore` ya es la authority durable del `knowledge_store`; `EnhancedRetriever` ya la consume en retrieval normal. **EXTEND**, no segundo memory store.
2. `knowledge_store.source` es string durable y transporta provenance familiar versionado sin migration.
3. La memoria episódica/working/semantic cruda permanece separada y no se copia wholesale. La proyección familiar parte de store curado y catálogos.
4. Skills conservan registry durable. El catálogo familiar se hereda como conocimiento/provenance; no instala instrucciones arbitrarias.
5. CapabilityRegistry/CapabilityStore distinguen inventory de `verified_available` y exigen authority/evidence/observedAt. Capability verificada en parent no se convierte en execution-ready del child por herencia.
6. La query selectiva reutiliza `ColonyMessaging` `peer_query`/`peer_response`, Social relay, inbox durable y KV; no introduce segundo transporte, poller o memory authority.
