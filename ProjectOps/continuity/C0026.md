## Decisión arquitectónica

### 1. Ledger realizado se conserva

`transactions` sigue siendo authority de movimientos materializados/realizados. No se insertará una transaction como realizada cuando provider sólo diga `submitted/processing/pending` o el resultado de dispatch sea UNKNOWN.

### 2. Crear sólo un owner estrecho de external financial effects

Se autoriza `CREATE_NARROW` de una state machine persistente para **financial effect intent/reconciliation**, no otra treasury/ledger.

Debe poseer únicamente:
- durable logical operation/idempotency key;
- effect kind + canonical semantic fingerprint;
- amount + unidad;
- recipient/child cuando aplique;
- provider external id/status observado;
- estado pre-dispatch / pending-or-unknown / settled / rejected / reconciliation-required o equivalentes;
- timestamps y evidence/provenance mínima.

No poseerá P&L, balances derivados, opportunity state, strategic prediction/outcome ni policy authority.

### 3. Idempotencia antes del side effect

- persistir intent ANTES de dispatch;
- usar su durable key como provider idempotency key;
- un logical effect equivalente no puede volver a dispatch mientras exista un effect no terminal compatible;
- ambiguous transport/5xx -> UNKNOWN/PENDING, no retry ciego;
- explicit reject -> rejected, sin transaction;
- explicit settled observation -> materialización idempotente de transaction + child bookkeeping cuando corresponda;
- settled externally + local projection failure -> reconciliation-required, no success ficticio ni second transfer.

### 4. Clasificación rica de provider status

Reemplazar la semántica binaria `isCreditTransferAccepted()` por clasificación material:
- explicit negative -> REJECTED;
- explicit final settlement/success -> SETTLED;
- submitted/processing/pending/queued/empty/unrecognized -> PENDING_OR_UNKNOWN.

UNKNOWN nunca se convierte en SETTLED por ausencia de palabras negativas.

### 5. Unificar callers sobre el mismo execution/reconciliation adapter

El mismo adapter debe ser usado por:
- `transfer_credits`;
- `fund_child`;
- `SimpleFundingProtocol.fundChild()` / orchestrator funding.

Así desaparece la divergencia semántica actual sin crear otro transport.

### 6. Treasury projection causal

Crear/EXTEND una proyección de dominio que componga owners existentes y calcule, sólo cuando la evidencia lo permita:
- observed parent credits/cash por autoridad y unidad;
- active commitments desde task graph;
- pending/unknown financial effects como capital inmovilizado, no realizado;
- explicit reserves/contingency inputs;
- internal capital allocated/returned;
- realized known operating costs;
- child economics existentes;
- free capital sólo si balance observado y deductions requeridas son conocidas.

Si balance o una deducción material necesaria es UNKNOWN, free capital permanece UNKNOWN; no se sustituye con cero.

### 7. Thresholds

- eliminar el universal `50% balance` de tool paths;
- caps configurables existentes pueden persistir inicialmente como guard/risk signal transicional, pero no se presentarán como verdad económica universal;
- no introducir otro porcentaje fijo de reserva/reinvestment/distribution.

### 8. Learning y judgment

- REUSE P-023 prediction→outcome;
- REUSE P-025 Strategic Cognition para ordinary/extraordinary decisions;
- REUSE P-027 opportunity portfolio;
- Treasury emitirá/consumirá referencias económicas causales, no tablas paralelas de predictions/outcomes.
