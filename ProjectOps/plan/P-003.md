## Objetivo

Reauditar, reconciliar e integrar correctamente el trabajo existente de PR #29 contra el runtime vigente, sin reemplazarlo por una implementación paralela y sin fabricar autoridad económica.

## Problema resuelto

ABOS necesitaba distinguir causalmente:
- parent funding histórico;
- child live balance;
- internal capital allocation/return;
- realized task cost;
- estimated commitments;
- attributed revenue;
- external P&L;
- profitability;
- ROI.

El runtime no debe inventar equivalencias entre esos conceptos ni producir decisiones automáticas desde datos UNKNOWN.

## Semántica obligatoria preservada

- unknown != zero;
- unknown profitability != unprofitable;
- funding != balance;
- funding != expense;
- internal capital flow != external P&L;
- realized cost != estimate/commitment;
- ROI no existe sin numerator/denominator válidos;
- parent bookkeeping no sustituye live child observation;
- efecto externo aceptado != persistencia local confirmada;
- HTTP success con status económico explícitamente negativo no acredita allocation.

## Implementación final

### Ledger y funding

- `TransactionType` incorpora `capital_allocation` y `capital_return`.
- `transactions.type` sigue siendo TEXT sin CHECK; no se introdujo migration innecesaria.
- `SimpleFundingProtocol.fundChild()` y `fund_child` registran nuevas transferencias parent→child como capital interno.
- `children.funded_amount_cents` sigue siendo bookkeeping histórico; no se presenta como saldo.
- `SimpleFundingProtocol.getBalance()` devuelve `null` mientras el parent carezca de authority real para observar child balance.
- `recallCredits()` usa tracked allocation sólo como bookkeeping/reason de unavailable.

### Efecto externo y persistencia

- Transferir créditos es la frontera externa irreversible.
- `isCreditTransferAccepted()` centraliza aceptación y rechaza marcadores explícitos de failure/error/rejection/decline/cancel/denied/invalid sin usar una allowlist cerrada.
- Ledger + funded amount se persisten atómicamente después de un efecto externo aceptado.
- External success + local SQLite failure se reporta como reconciliation gap y no como señal que invite a repetir ciegamente la transferencia.
- `fund_child` no avanza lifecycle a `funded` si la persistencia local falló.

### Financial report

`colony_financial_report` ya no fabrica business P&L desde tipos ambiguos:
- `revenueCents`, `expenseCents`, `netCents` quedan `null` sin autoridad causal;
- generic `transfer_in/out` permanecen unclassified;
- `credit_purchase` no se presenta como revenue;
- inference/tool costs se reportan como known operating cost;
- funding requests se separan;
- capital allocated/returned se separa del P&L;
- child snapshots mantienen UNKNOWN balance/revenue/ROI cuando corresponde.

Histórico ambiguo `transfer_out` no se migró heurísticamente.

### Health y planning

- child balance UNKNOWN permanece null;
- HealthMonitor sólo detecta `out_of_credits` desde un número observado;
- auto-funding rehúsa operar desde UNKNOWN;
- planner no reutiliza FundingProtocol child como parent-balance authority;
- sin observación/caché válida, parent `creditsCents` permanece null y `survivalTier` unknown;
- prompt muestra `UNKNOWN`, no `0 cents` ficticios.
