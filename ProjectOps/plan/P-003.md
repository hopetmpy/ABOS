## Problema que resuelve

- parent funding histórico;
- child live balance;

- unknown != zero;
- unknown profitability != unprofitable;
- funding != balance;
- funding != expense;
- internal capital flow != external P&L;
- realized cost != estimate/commitment;
- ROI no existe sin numerator/denominator válidos;
- parent bookkeeping no sustituye live child observation;
- efecto externo aceptado != persistencia local confirmada;
- una respuesta HTTP exitosa con status económico explícitamente negativo no acredita allocation.

## Implementación reconciliada

### Ledger y funding

- `TransactionType` incorpora `capital_allocation` y `capital_return`.
- `transactions.type` sigue siendo TEXT sin CHECK; no se introdujo migration innecesaria.
- `SimpleFundingProtocol.fundChild()` y `fund_child` registran nuevas transferencias parent→child como capital interno, no `transfer_out` genérico.
- `children.funded_amount_cents` sigue siendo bookkeeping histórico; no se renombra ni se presenta como saldo.
- `SimpleFundingProtocol.getBalance()` devuelve `null` mientras el parent carezca de autoridad para observar el saldo Conway del child por address.
- `recallCredits()` usa tracked allocation sólo para bookkeeping/reason de unavailable; no inventa un child debit.

### Efecto externo y persistencia

- Transferir créditos es la frontera externa irreversible.
- La aceptación de transferencia está centralizada en `isCreditTransferAccepted()`; usa mundo abierto para status positivos/futuros y rechaza marcadores explícitos de failure/error/rejection/decline/cancel/denied/invalid.
- La persistencia local de ledger + funded amount es atómica después de un efecto externo aceptado.
- Si el efecto externo ocurrió y SQLite local falla, el runtime no devuelve una señal que invite a repetir ciegamente la transferencia; registra la evidencia faltante para reconciliación.
- `fund_child` no avanza lifecycle a `funded` cuando la persistencia local de capital falló.

### Financial report

`colony_financial_report` ya no fabrica business P&L desde tipos ambiguos:
- `revenueCents`, `expenseCents`, `netCents` quedan `null` sin autoridad causal;
- generic `transfer_in` / `transfer_out` permanecen explícitamente unclassified;
- `credit_purchase` queda como resource acquisition, no revenue;
- inference/tool costs se reportan como known operating cost observado;
- funding requests se reportan separadamente;
- capital allocated/returned y net internal capital flow se separan del P&L;
- child snapshots muestran funding histórico, task costs/commitments y UNKNOWN balance/revenue/ROI cuando corresponde.

Las filas históricas `transfer_out` no se migran heurísticamente: no existe evidencia suficiente para distinguir antiguo child funding de transferencias externas legítimas.

### Health y planning

- balance child UNKNOWN permanece null;
- HealthMonitor sólo puede detectar `out_of_credits` desde un número realmente observado;
- auto-funding rehúsa operar desde UNKNOWN;
- planner context no llama al FundingProtocol de children con la dirección del parent;
- sin observación explícita ni cache válida del parent, `creditsCents` queda null y `survivalTier` queda `unknown`;
- el prompt muestra `UNKNOWN`, no `0 cents` ficticios.
