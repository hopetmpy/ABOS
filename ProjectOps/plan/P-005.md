## Objetivo

Elevar únicamente los claims que realmente requieren proveedores, cuentas, wallets, infraestructura, dinero o servicios externos. Source/CI/E4 local no se promocionan artificialmente a E5/E6.

## Fronteras conocidas y extensibles

### A. ChatGPT / Codex OAuth y model discovery

Cuando exista autorización humana legítima: device-code/session real, model discovery real, inference por la misma conexión, reasoning/model switching según contrato, restart/logout y ausencia de token leaks.

### B. AWS / cloud billable lifecycle

Con cuenta/presupuesto/autorización: readiness/auth, provision, bootstrap/health, task/artifacts requeridos, recovery/cleanup y costo observado. Resource ownership/idempotency obligatorios.

### C. MCP/servicios externos autenticados

P-015 puede cerrar source/integration con server local/test. Para un endpoint MCP/API remoto que forme parte de un claim de release: auth real, discovery/call, policy, failure/reconnect y no secret logging.

### D. Child/external environment LIVE

Cuando el claim requiera sandbox/child real: birth/runtime health/constitution/communication/authority observados en el entorno real. Parent bookkeeping no sustituye señales child.

### E. Economic LIVE

Saldos, costos externos, revenue, payments, profitability o ROI sólo E6 cuando las autoridades reales necesarias fueron observadas/atribuidas causalmente. Experimentos de P-027 y treasury P-030 no fabrican revenue desde expectations.

### F. Resource acquisition LIVE

Si P-031 realiza una compra/provision real: authorization, commitment/price, usable resource, cancellation/cleanup y realized cost deben reconciliarse.

La lista es un inventario de fronteras conocidas, no allowlist: futuras integraciones externas se añaden si el release/claim las requiere.

## Clasificación cuando no puede ejecutarse

- `LIVE_BLOCKED_EXTERNAL / UNAUTHORIZED`: falta permiso/credencial humana.
- `LIVE_BLOCKED_EXTERNAL / UNAVAILABLE`: provider/entorno no disponible.
- `LIVE_BLOCKED_EXTERNAL / BUDGET`: coste no autorizado.
- SOURCE/INTEGRATION pueden permanecer PASS si fueron demostrados separadamente.

## Reglas

- no gastar dinero para validar cambios no relacionados;
- billable tests definen cap/cleanup antes de crear recursos;
- no secrets/tokens/private keys en ProjectOps;
- failure de una frontera no prueba que el objetivo global sea imposible;
- P-005 puede quedar PARCIAL/BLOQUEADO por subfronteras sin ocultar código pendiente.

## Definition of Done

P-005 queda HECHO sólo cuando las fronteras LIVE declaradas necesarias para la release/objetivo vigente estén verificadas o explícitamente retiradas por decisión canónica. Al cerrar P-036, cualquier subfrontera aún externa debe quedar enumerada y clasificada, nunca fingida como PASS.
