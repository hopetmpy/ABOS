# P-005 — Ejecutar acceptance LIVE de fronteras externas críticas

State: PLANIFICADO
Priority: MEDIA

Required-Context:
- `AGENTS.md`
- `ProjectOps/PROJECT.md`
- `ProjectOps/CONTINUITY.md`
- `src/codex/`
- `src/ai-connections/`
- `src/environments/`
- `src/identity/`
- `src/replication/`
- `.github/workflows/ci.yml`

## Objetivo

Cerrar de forma incremental los claims que requieren evidencia externa real y que source/CI no pueden certificar por sí solos.

## Fronteras conocidas

### A. ChatGPT / Codex device-code

PR #16 implementó la ruta y dejó explícito que la autorización humana LIVE no fue ejecutada en CI.

Acceptance mínima cuando exista autorización:
- device-code emitido por proveedor real;
- autorización completada legítimamente;
- session/account status consistente;
- model discovery real;
- una inference real por la misma ruta;
- logout/restart/refresh behavior según contrato;
- ningún token secreto registrado en ProjectOps.

### B. AWS lifecycle billable

PR #13 y fases posteriores implementaron/simularon el control-plane, pero no acreditaron un EC2 billable LIVE en CI.

Acceptance mínima cuando exista cuenta/presupuesto/autorización:
- readiness/auth real;
- provisioning con ownership/idempotency correctos;
- bootstrap/runtime health;
- Task execution/artifact behavior requerido;
- suspend/resume/recovery/cleanup según scope del test;
- costo observado y resource cleanup verificados;
- ningún secret persistido en ProjectOps.

### C. Economic LIVE cuando un claim lo exija

Saldos/revenue/profitability de agents/children no se certifican desde bookkeeping parcial. Solo abrir acceptance económica específica cuando exista una autoridad observable para la señal necesaria.

## Reglas

- P-005 puede ejecutarse por subfrontera; no requiere gastar dinero para validar cambios no relacionados.
- Si falta autorización, estado = BLOQUEADO/UNAUTHORIZED, no FAIL del source.
- Si un provider no está disponible, conservar UNAVAILABLE/UNKNOWN según evidencia.
- Tests billables requieren presupuesto, cleanup y límites antes de provisioning.
- Nunca registrar credenciales, tokens, private keys o datos sensibles en ProjectOps.

## Evidence ladder

El objetivo de cada subfrontera es elevar únicamente el claim correspondiente a E5/E6. No convierte todo ABOS en E7.

## Criterios de aceptación

Para cada subfrontera ejecutada:
- prerequisitos/autorización explícitos;
- procedure reproducible;
- logs/resultados no secretos;
- cleanup/recovery comprobado cuando aplique;
- claim exacto y nivel E registrado;
- failures clasificados sin inventar imposibilidad.

## Definición de HECHO

P-005 queda HECHO cuando las fronteras externas declaradas como necesarias para la release/objetivo vigente hayan sido ejecutadas o explícitamente retiradas por decisión canónica. Puede permanecer PARCIAL/BLOQUEADO sin frenar trabajo source independiente.
