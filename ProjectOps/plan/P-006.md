## Objetivo

Restaurar `pnpm audit` green mediante una remediación compatible y auditada de advisories actuales, sin ocultarlos ni ignorarlos globalmente, y dejar ABOS sobre runtimes Node mantenidos y realmente soportados por su dependency graph.

## Hallazgo que origina el P

Durante la validación del cutover ProjectOps, el job `security-audit` falló con tres findings moderados:

1. `stream-json <=3.4.0` — advisory `GHSA-528h-pc64-c93x`, path observado `.>@solana/web3.js>jayson>stream-json`, patched `>=3.5.0`.
2. `vitest >=2.1.0 <4.1.11` — advisory `GHSA-82fw-gwwq-j7x9`, direct dev dependency.
3. `@vitest/mocker >=2.1.0 <4.1.11` — mismo advisory transitivo vía Vitest.

La rama ProjectOps no introdujo esos findings. Son deuda preexistente descubierta durante validación.

## Evidencia discriminante obtenida durante P-006

### Vitest

- `vitest@4.1.11` + `@vitest/mocker@4.1.11` limpia sus advisories.
- El primer intento de suite de seguridad falló antes de ejecutar tests porque Vitest 4 ya no acepta `--grep`.
- `test:security` y `test:financial` usan esa sintaxis legacy; el equivalente vigente es `--testNamePattern` / `-t`.
- Después de migrar ambos scripts, security tests, financial tests y full `test:ci` pasaron en el probe Node 22.

### stream-json / Node 20

- Forzar `stream-json@3.6.0` limpia el advisory y el smoke Solana JSON-RPC pasa en Node 22.
- El CI limpio en Node `20.20.2` falla en `pnpm install --frozen-lockfile` porque `stream-chain@4.2.5` declara Node `>=22`.
- La versión parcheada mínima `stream-json@3.5.0` también declara Node `>=22` y depende de `stream-chain ^4.2.5`; por tanto no existe una release upstream parcheada compatible con la antigua lane Node 20.
- Node 20 está EOL y ya no recibe fixes de seguridad; conservarlo exigiría ignorar engines, mantener una fork/patch no reconocida por audit o aceptar el advisory. Esas rutas contradicen el objetivo de P-006.

### Node 24 / better-sqlite3

- README registra que Node 24 fue rechazado anteriormente porque `better-sqlite3` 11 no tenía el prebuild necesario y caía a node-gyp en Windows.
- `better-sqlite3` 13 migró a N-API, declara Node `>=22` y publica prebuilds empaquetados, eliminando la razón histórica principal para bloquear Node 24.
- La decisión revisada es validar las dos LTS mantenidas: Node 22 y Node 24. Node 22 permanece default/recommended hasta que evidencia de release indique lo contrario.

## Decisión revisada

La evidencia invalida el supuesto original “preservar Node 20/22”. P-006 pasa a remediar seguridad y runtime de forma conjunta:

1. Vitest → línea 4 patched y scripts CLI compatibles con Vitest 4.
2. `stream-json` vulnerable → versión patched mediante override selectivo.
3. Node support → retirar Node 20 EOL y validar Node 22 + Node 24.
4. `better-sqlite3` → línea 13 N-API para eliminar el bloqueo histórico de Node 24 y conservar instalación prebuilt en plataformas soportadas.
5. Mantener `.nvmrc` / `.node-version` en 22 por estabilidad y porque Node 22 sigue siendo LTS soportada.
6. No elevar `@solana/web3.js` sólo por este advisory mientras la ruta actual pase pruebas.

Esto no es una reducción arbitraria de capacidad: retira una runtime EOL cuyo dependency graph seguro ya no la soporta y añade otra LTS mantenida que antes estaba bloqueada por una limitación técnica ya resuelta upstream.

## Auditoría previa obligatoria restante

1. regenerar lockfile con las versiones decididas desde la base actual;
2. seguir cualquier cambio de `better-sqlite3` 11→13 sobre schema/migrations/transactions y tipos usados por ABOS;
3. validar instalación/build/tests en Node 22 y 24;
4. validar Windows en Node 22 y 24 para detectar prebuild/fallback nativo;
5. validar `pnpm audit`, security/financial tests y full suite;
6. validar installer/rebrand contract y documentación de runtimes;
7. no aceptar excepción de audit para ocultar el advisory;
8. integrar sólo con CI actual y revalidar sobre el SHA de `main`.

## Semántica a preservar

- no degradar CI para volverlo verde;
- no bajar severidad ni ignorar el advisory;
- no eliminar tests para ocultar fallos;
- no cambiar wallet/Solana behavior sólo para resolver una transitiva;
- `engine-strict=true` permanece: una runtime no soportada debe fallar temprano;
- el installer y README deben reflejar exactamente las lanes probadas;
- cambio de runtime support debe estar respaldado por evidencia, no por conveniencia;
- no declarar fixed hasta que el audit del lockfile integrado pase.

## Criterios de aceptación revisados

- `pnpm audit`: PASS sin advisories ignorados;
- Node 22: frozen install + typecheck + build + full tests + security tests PASS;
- Node 24: frozen install + typecheck + build + full tests + security tests PASS;
- Windows Node 22 y 24: instalación/build/smoke/regressions PASS, sin dependencia obligatoria de toolchain local para el camino normal;
- `test:security` y `test:financial` compatibles con Vitest 4 y PASS;
- public distribution smoke PASS sobre el SHA integrado;
- installer/rebrand/runtime docs coherentes con 22/24 y default 22;
- diff de dependency graph auditado;
- ProjectOps reconciliado con evidencia.

## Definición de HECHO

HECHO solo cuando el security-audit autoritativo y las lanes Node 22/24 pasen sobre el SHA integrado en `main`, Windows/public distribution no muestren regresiones y ProjectOps registre el cambio exacto de contrato y evidencia.
