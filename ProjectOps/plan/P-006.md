## Objetivo

Restaurar `pnpm audit` green mediante una remediación compatible y auditada de advisories actuales, sin ocultarlos ni ignorarlos globalmente, y dejar ABOS sobre runtimes Node mantenidos y realmente soportados por su dependency graph.

## Hallazgo que origina el P

Durante la validación del cutover ProjectOps, el job `security-audit` falló con tres findings moderados:

1. `stream-json <=3.4.0` — advisory `GHSA-528h-pc64-c93x`, path observado `.>@solana/web3.js>jayson>stream-json`, patched `>=3.5.0`.
2. `vitest >=2.1.0 <4.1.11` — advisory `GHSA-82fw-gwwq-j7x9`, direct dev dependency.
3. `@vitest/mocker >=2.1.0 <4.1.11` — mismo advisory transitivo vía Vitest.

La rama ProjectOps no introdujo esos findings. Son deuda preexistente descubierta durante validación.

## Evidencia discriminante obtenida durante P-006

### Vitest 4

- `vitest@4.1.11` limpia el advisory directo y el de `@vitest/mocker` transitivo.
- El primer intento de suite de seguridad falló antes de ejecutar tests porque Vitest 4 retiró `--grep`.
- `test:security` y `test:financial` usaban esa sintaxis legacy y fueron migrados a `--testNamePattern`.
- Security tests, financial tests y full suite pasaron después de la migración.

### stream-json / Node 20

- El override selectivo `stream-json@<=3.4.0 -> 3.6.0` limpia el advisory sin elevar `@solana/web3.js`.
- Un smoke JSON-RPC de Solana pasó con ese graph.
- Node `20.20.2` falla en frozen install porque `stream-chain@4.2.5`, dependencia de la línea parcheada de `stream-json`, exige Node `>=22`.
- La línea parcheada mínima de `stream-json` también exige Node `>=22`; no existe release upstream parcheada compatible con la antigua lane Node 20.
- Node 20 está EOL. Conservarlo requeriría ignorar engines, aceptar el advisory o mantener una fork/patch propia. P-006 rechaza esas rutas.

### Node 24 / better-sqlite3

El antiguo bloqueo de Node 24 era real, pero específico del graph previo: `better-sqlite3` 11 podía caer a compilación nativa en Windows.

Se probaron alternativas en lugar de asumir una actualización:

1. **`better-sqlite3@13.0.3` — DESCARTADO para este release.**
   - fresh install Windows Node 24 cayó a `node-gyp rebuild`;
   - el runner no tenía toolchain Visual Studio utilizable;
   - exigir toolchain C++ para una instalación normal habría degradado la distribución.
2. **`better-sqlite3@12.12.0` — DESCARTADO.**
   - existía como release upstream observada, pero no estaba publicado en el registry npm canónico;
   - `pnpm` devolvió `ERR_PNPM_NO_MATCHING_VERSION`.
3. **`better-sqlite3@12.11.1` — CANDIDATO VALIDADO.**
   - es una 12.x publicada;
   - declara compatibilidad con Node 22 y 24;
   - frozen install Windows 22 y Windows 24 pasó sin convertir la instalación normal en un build C++ manual;
   - typecheck, build, state smoke y portability regressions pasaron en ambas lanes.

## Decisión final de implementación

1. Vitest → `^4.1.11` con scripts CLI compatibles con Vitest 4.
2. `stream-json` vulnerable → override selectivo `stream-json@<=3.4.0 -> 3.6.0`.
3. `@solana/web3.js` permanece en su línea actual porque no se necesitó elevarlo para corregir el advisory.
4. Node support → Node 22 + Node 24; Node 22 permanece default/recommended.
5. `better-sqlite3` → `^12.11.1`, validado en Windows 22/24 y Linux CI.
6. `engine-strict=true` permanece.
7. No se exige toolchain nativo adicional como requisito normal del usuario.

Esto no es una reducción arbitraria de capacidad: retira Node 20 EOL, cuyo graph seguro ya no es soportado upstream, y añade Node 24 como LTS demostrada por CI.

## Semántica a preservar

- no degradar CI para volverlo verde;
- no bajar severidad ni ignorar advisories;
- no eliminar tests para ocultar fallos;
- no cambiar wallet/Solana behavior sólo para resolver una transitiva;
- `engine-strict=true` permanece;
- installer, package engines, CI y README deben contar la misma verdad;
- no confundir release upstream con versión realmente publicada en registry;
- cambio de runtime support debe estar respaldado por evidencia;
- no declarar fixed hasta que el graph se integre y vuelva a pasar en `main`.

## Criterios de aceptación revisados

- `pnpm audit`: PASS sin advisories ignorados;
- Node 22: frozen install + typecheck + build + full tests + security tests PASS;
- Node 24: frozen install + typecheck + build + full tests + security tests PASS;
- Windows Node 22 y 24: instalación/build/smoke/regressions PASS;
- `test:security` y `test:financial` compatibles con Vitest 4 y PASS;
- public distribution smoke PASS en 22/24;
- installer/rebrand/runtime docs coherentes con 22/24 y default 22;
- dependency graph y lockfile deterministas auditados;
- ProjectOps reconciliado con evidencia;
- después de merge: mismos gates aplicables PASS sobre `main`.

## Definición de HECHO

HECHO solo cuando el security-audit autoritativo y las lanes Node 22/24 pasen sobre el SHA integrado en `main`, Windows/public distribution no muestren regresiones y ProjectOps registre el cambio exacto de contrato y evidencia.
