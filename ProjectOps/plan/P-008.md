## Objetivo

Crear un contrato único para que prompts, planner, UI/CLI, children y runtime nunca presenten una capacidad como disponible sólo porque existe código, un paquete instalado, una descripción o un test aislado.

## Estado observado

La auditoría detectó capacidades escritas/instalables/descriptas que no equivalen a ejecución funcional real. Este P no asume que cada caso sigue igual al ejecutarse: reaudita productores/consumidores antes de modificar.

## Arquitectura objetivo

Toda capability observable debe poder expresarse al menos como: DISCOVERED_UNVERIFIED, ACQUIRED, PROBED, VERIFIED_AVAILABLE, DEGRADED, UNAVAILABLE, UNAUTHORIZED, PROHIBITED o UNKNOWN. Los nombres exactos se reconciliarán con tipos existentes; no se crea un enum cerrado si el source ya posee un modelo extensible.

Los prompts/status se derivan de autoridad runtime verificable y provenance, no de listas hardcodeadas o marketing interno.

## Invariantes

- source/test/install != capability success;
- UNKNOWN no se promociona por optimismo;
- una capability puede degradarse/retirarse sin borrar historia;
- amplitud no autoriza claims falsos;
- no crear un segundo CapabilityRegistry.

## Preguntas/falsación

¿Existe ya un lifecycle equivalente? ¿Qué módulos escriben capabilities al prompt? ¿Qué tests validan claims y cuáles sólo estructura? ¿Puede un provider desaparecer entre discovery y call? ¿Qué ocurre tras restart?

## Plan técnico

1. mapear todos los productores y consumidores de capability/status;
2. elegir/extender autoridad canónica;
3. definir transitions/evidence mínimas;
4. reconciliar prompt/status/runtime;
5. añadir tests de overclaim, degradation y restart;
6. integrar con P-013 observability y P-014 Capability Fabric.

## Failure/rollback

Migración de estados debe aceptar registros legacy y conservar UNKNOWN. Rollback no puede convertir registros nuevos en disponibilidad ficticia.

## Definition of Done

No existe ruta material donde ABOS anuncie una capacidad ejecutable sin autoridad/evidencia correspondiente; tests adversariales demuestran la separación entre discovered/installed/probed/verified.
