## Objetivo

Crear un contrato único para que prompts, planner, UI/CLI, children y runtime nunca presenten una capacidad como disponible sólo porque existe código, un paquete instalado, una descripción o un test aislado.

## Arquitectura objetivo

Toda capability observable puede expresarse al menos como semántica equivalente a: DISCOVERED_UNVERIFIED, ACQUIRED, PROBED, VERIFIED_AVAILABLE, DEGRADED, UNAVAILABLE, UNAUTHORIZED, PROHIBITED o UNKNOWN. El modelo permanece extensible y de mundo abierto.

`CapabilityRegistry` permanece como authority genérica única en memoria. `available` legacy sobrevive únicamente como proyección derivada de estado/evidence más ricos.

Los producers evidence-rich, en particular environment providers, proyectan availability/evidence/observedAt al registry mediante `registerEnvironmentSnapshot()`. Los consumers operativos sólo elevan `use_existing` desde evidencia actualmente suficiente.

Prompt/status/list deben distinguir explícitamente:
- soporte arquitectónico;
- definición cargada;
- instalación/configuración;
- autorización;
- probe/observation;
- `VERIFIED_AVAILABLE`.

## Invariantes

- source/test/install != capability success;
- UNKNOWN no se promociona por optimismo;
- una capability puede degradarse/retirarse sin borrar historia;
- amplitud no autoriza claims falsos;
- no crear un segundo CapabilityRegistry;
- no cerrar el mundo de providers/capabilities artificialmente;
- availability derivada conserva evidence/authority/temporalidad suficientes;
- `VERIFIED_AVAILABLE` requiere evidence no vacía y observación temporal válida;
- restart no promueve availability por pérdida de evidence fresca;
- configuración MCP no equivale a ejecución MCP;
- una ruta MCP sin adapter real no puede devolver éxito aparente;
- P-008 no implementa prematuramente P-014 ni P-015.

## Hipótesis — resolución vigente

H1 — CONFIRMADA. El booleano `available` y la promoción por existencia eran causa material de overclaim.

H2 — PARCIALMENTE FALSADA / REUTILIZADA. No existe otro lifecycle genérico canónico que deba sustituir `CapabilityRegistry`; sí existe evidence rica en `environments` que debe proyectarse al registry.

H3 — CONFIRMADA. `available` puede mantenerse como compatibilidad derivada, nunca como authority independiente.

H4 — CONFIRMADA PARCIALMENTE. Producers que realmente inspeccionan/proban pueden elevar disponibilidad con provenance; inventario/tool definition/enabled por sí solos no.

H5 — FALSADA. `loadInstalledTools()` no carga filas disabled: `getInstalledTools()` ya aplica `WHERE enabled = 1`. El defecto restante era `enabled/installed != verified readiness`.

H6 — CONFIRMADA. El executor MCP nominal constituía false-success; debía cerrarse sin construir el runtime MCP de P-015.

## Decisión técnica

Clasificación dominante: **EXTEND + UNIFY + CORRECT**, no CREATE.

1. Extender descriptor lifecycle/evidence conservando compatibilidad.
2. Normalizar todo registro en `CapabilityRegistry`.
3. Requerir evidence + `observedAt` válido antes de aceptar `verified_available`.
4. Resolver sólo consume verified evidence para `use_existing` y preserva UNAUTHORIZED/PROHIBITED/UNKNOWN.
5. Proyectar environment observations con authority/evidence/temporalidad.
6. Tratar tool/skill existence como discovered/unverified salvo producer evidence-rich.
7. Revalidar persisted skills al restart.
8. Corregir claims del system prompt/planner/status para separar architectural support / loaded inventory de runtime readiness.
9. Mantener MCP configurado como inventory unverified y no inference-callable hasta que P-015 entregue un adapter real/verificado.
10. Preservar un fail-closed defense-in-depth si una ruta intenta ejecutar MCP nominal directamente.
