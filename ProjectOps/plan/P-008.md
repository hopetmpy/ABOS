## Objetivo

Crear un contrato único para que prompts, planner, UI/CLI, children y runtime nunca presenten una capacidad como disponible sólo porque existe código, un paquete instalado, una descripción o un test aislado.

## Estado observado

Intervención activa sobre `abos/p008-runtime-truth-v1`, abierta desde `main` `fed2fe3c836dfc4351934a4abedf78898782728e`.

La auditoría y ejecución ya alcanzaron `DECISION_READY` para el contrato core y confirmaron:
- `CapabilityDescriptor.available` era insuficiente como authority por sí solo;
- `CapabilityRegistry` ya es la authority genérica adecuada y debe EXTEND/UNIFY, no duplicarse;
- `src/environments/` posee evidence/availability/observedAt reutilizable y no debe convertirse en una segunda generic capability authority;
- tool definition, installed/enabled y skill enabled son inventario/discovery, no readiness;
- `CapabilityResolver.use_existing` sólo debe aceptar `VERIFIED_AVAILABLE` con evidence temporal suficiente;
- restart de skills debe revalidar requisitos actuales y no reactivar inventario stale;
- prompts no deben convertir arquitectura o tool definitions cargadas en claims de disponibilidad;
- `AbosDatabase.getInstalledTools()` sí filtra `enabled = 1`; la hipótesis preliminar contraria quedó falsada;
- installed MCP continúa siendo una frontera material: hoy existe configuración nominal cuyo executor no implementa protocolo MCP real. P-015 sigue siendo la authority de implementación MCP; P-008 debe evitar cualquier claim de readiness/success que derive sólo de instalación/configuración.

## Arquitectura objetivo

Toda capability observable debe poder expresarse al menos como semántica equivalente a: DISCOVERED_UNVERIFIED, ACQUIRED, PROBED, VERIFIED_AVAILABLE, DEGRADED, UNAVAILABLE, UNAUTHORIZED, PROHIBITED o UNKNOWN. El modelo debe permanecer extensible y de mundo abierto.

`CapabilityRegistry` permanece como authority genérica única en memoria. `available` legacy sobrevive únicamente como proyección derivada de un estado/evidencia más rico.

Los producers evidence-rich, en particular environment providers, proyectan availability/evidence/observedAt al registry. Los consumers operativos sólo elevan `use_existing` desde evidencia actualmente suficiente.

Prompt/status deben distinguir explícitamente:
- soporte arquitectónico;
- definición cargada;
- instalación/configuración;
- autorización;
- probe/observation;
- `VERIFIED_AVAILABLE`.

## Invariantes

- source/test/install != capability success;
- UNKNOWN no se promociona por optimismo;
- una capability puede degradarse/retirarse sin borrar historia;
- amplitud no autoriza claims falsos;
- no crear un segundo CapabilityRegistry;
- no cerrar el mundo de providers/capabilities artificialmente;
- availability derivada debe conservar evidence/authority/temporalidad suficientes;
- `VERIFIED_AVAILABLE` requiere evidence no vacía y observación temporal válida;
- restart no puede promover availability por pérdida de evidence fresca;
- configuración MCP no equivale a ejecución MCP;
- P-008 no implementa prematuramente el Capability Fabric completo de P-014 ni el protocolo MCP real de P-015.

## Hipótesis — resolución vigente

H1 — CONFIRMADA. El booleano `available` y la promoción por existencia eran una causa material de overclaim.

H2 — PARCIALMENTE FALSADA / REUTILIZADA. No existe otro lifecycle genérico canónico que deba sustituir `CapabilityRegistry`; sí existe evidence rica en `environments` que debe proyectarse al registry.

H3 — CONFIRMADA. `available` puede mantenerse como compatibilidad derivada, nunca como authority independiente.

H4 — CONFIRMADA PARCIALMENTE. Producers que realmente inspeccionan/proban pueden elevar disponibilidad con provenance; inventario/tool definition/enabled por sí solos no.

H5 — FALSADA. `loadInstalledTools()` no carga filas disabled: `getInstalledTools()` ya aplica `WHERE enabled = 1`. El defecto restante es `enabled/installed != verified readiness`.

## Decisión técnica

Clasificación dominante: **EXTEND + UNIFY + CORRECT**, no CREATE.

1. Extender el descriptor lifecycle/evidence conservando compatibilidad.
2. Normalizar todo registro en `CapabilityRegistry`.
3. Requerir evidence + `observedAt` válido antes de aceptar `verified_available`.
4. Hacer que resolver sólo consuma verified evidence para `use_existing` y preserve UNAUTHORIZED/PROHIBITED/UNKNOWN sin colapsarlos.
5. Proyectar environment observations con authority/evidence/temporalidad.
6. Tratar tool/skill existence como discovered/unverified salvo producer evidence-rich.
7. Revalidar persisted skills al restart.
8. Reescribir claims del system prompt para separar architectural support / loaded surfaces de runtime readiness.
9. No simular MCP real; hasta P-015, instalación/configuración MCP no puede ser prueba de ejecución.

## Failure/rollback

Migración de estados acepta registros legacy y conserva UNKNOWN. Rollback no puede convertir registros nuevos en disponibilidad ficticia. Cualquier proyección `available` backward-compatible deriva de evidence explícita.

Los cambios de prompt son semánticos, no una reducción arbitraria de capacidades: si una capability está realmente disponible, ABOS puede usarla; sólo se elimina el claim anticipado.

## Definition of Done

No existe ruta material donde ABOS anuncie una capacidad ejecutable sin authority/evidence correspondiente; tests adversariales demuestran la separación entre discovered/installed/probed/verified y la degradación/restart no elevan claims ficticios.
