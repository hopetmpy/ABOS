## Objetivo

Convertir policy de una clasificación parcial a una autoridad runtime consistente: permitir, denegar, requerir autorización/confirmación, poner en quarantine, reanudar o expirar decisiones sin perder provenance ni ejecutar el efecto antes del gate.

## Estado de la puerta

**DECISION_READY / IMPLEMENTATION_AUTHORIZED.**

C0006 registró la interrogación, hipótesis competidoras, bypasses materiales, authority a extender, migration/rollback y evidence ladder antes del primer cambio productivo. La implementación se ejecuta por unidades verificables; DECISION_READY no equivale a HECHO.

## Problemas a auditar

- default allow y risk levels pueden no imponer el gate que el nombre sugiere;
- `executeTool()` y otros consumidores pueden depender de la presencia opcional de context/policy wiring; hay que demostrar si existe bypass real en paths canónicos o sólo una API interna parcial;
- validaciones chain-specific pueden asumir EVM donde existe Solana;
- quarantine/approval pueden carecer de persistence/continuation semantics reales;
- una autorización humana no debe convertirse en permiso global indefinido;
- approval tardío, duplicado, revocado o posterior a un cambio de recurso/coste no debe ejecutar un efecto stale;
- restart mientras una decisión espera approval debe preservar estado sin double execution;
- deny/prohibited debe seguir distinguido de technical failure/unavailable.

## Arquitectura objetivo

Decision record durable con scope de actor/acción/recurso/coste/tiempo, provenance P-009, constitution result, policy result, required authority, expiry/idempotency y continuation token seguro cuando proceda.

La solución debe extender/unificar autoridades existentes antes de crear nuevas. No se autoriza un segundo PolicyEngine, approval ledger, quarantine store o execution authority por conveniencia.

## Invariantes

- constitution prevalece sobre survival/economics;
- denial no se camufla como technical failure;
- no bypass equivalente de una prohibición;
- authorization scope mínimo y explícito;
- chain/provider validation usa la autoridad apropiada, no regex accidental;
- approval no ejecuta side effects antes del gate;
- continuation/restart no duplica efectos;
- provenance P-009 no se pierde ni se eleva;
- UNKNOWN/UNAUTHORIZED/PROHIBITED/UNAVAILABLE permanecen distintos;
- CI/E3 no se eleva a autorización LIVE/E5.

## Hipótesis de apertura

H1 — `policyEngine && turnContext` opcionales permiten un bypass real en alguna ruta ejecutable material.

H2 — el path canónico siempre aporta ambos y el defecto está en API/lifecycle incompleto, no en bypass runtime actual.

H3 — approval/quarantine son principalmente clasificación/narrativa sin continuation durable exact-once.

H4 — ya existe persistence/estado suficiente bajo otro nombre y la ruta correcta es EXTEND/UNIFY, no CREATE.

H5 — validaciones de actor/chain mezclan identidad EVM con autorización general y fallan para Solana u otros providers abiertos.

C0006 discriminó estas hipótesis antes de source productivo: H1 y H3 quedaron confirmadas; H2/H4 parcialmente confirmadas; H5 confirmada para `send_message` sin generalizarla a providers financieros. La evidencia detallada y la decisión arquitectónica permanecen en el segmento activo.

## Failure matrix

Approval llega tarde, restart mientras espera, recurso cambia, balance/coste cambia, duplicate approval, cancellation, revoked authorization, provider unavailable, child unreachable, stale continuation, replay y concurrent resume.

## Evidencia requerida

Como mínimo E3/INTEGRATION_VERIFIED para source/lifecycle local: tests adversariales + persistence/restart + exact branch/main CI cuando aplique. Autorizaciones/provider externos sólo se reclaman E5 si se ejercitan realmente.

## Definition of Done

Un flujo bloqueado puede persistir y reanudarse exactamente una vez con autorización válida; un deny/prohibited nunca ejecuta side effects; EVM/Solana y actors distintos usan validación/autoridad correctas; restart/late/duplicate/revoked approval no crea bypass ni double execution; no existe una authority paralela innecesaria; branch/main quedan integrados y revalidados; ProjectOps queda reconciliado.
