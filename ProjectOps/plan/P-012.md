## Objetivo

Permitir que ABOS evolucione su propio source sin que un build/test fallido deje el runtime activo roto ni se reporte success por el mero hecho de haber escrito archivos, preservando autonomía legítima mediante gates causales/transaccionales en vez de depender indefinidamente de un contador fijo de modificaciones.

## Riesgo observado

La auditoría encontró write-before-verify y snapshot/rollback best-effort. Debe reproducirse y seguir todos los entrypoints de self-mod antes de elegir mecanismo.

P-010 también identificó `rate.self_mod_hourly` (10/hour) como **guard anti-runaway transitorio**, no como definición universal de cuánto self-mod es racional. P-012 debe reauditarlo bajo `CAPABILITY_PRESERVATION_BEFORE_RESTRICTION`: conservarlo, hacerlo configurable, reemplazarlo o contextualizarlo según evidencia de concurrency, rollback, blast radius, verification cost y runtime health. No debe promoverse automáticamente a invariante permanente.

## Arquitectura objetivo

Request/provenance → protected-scope check → transactional workspace/snapshot → staged edits → dependency/supply-chain checks → typecheck/build/tests pertinentes → adversarial checks → atomic activation → post-activation probe → commit/audit record; ante fallo: no activation o rollback verificable.

El mecanismo exacto puede usar Git/worktree/temp tree/atomic rename según auditoría. No se fija la implementación antes de comparar alternativas.

## Invariantes

- constitution/core protection no se desactiva por self-mod;
- failure no devuelve success;
- active source nunca depende de una staging incompleta;
- modification record distingue proposed/staged/verified/activated/rolled_back;
- secrets/runtime state no se copian al repo/staging;
- un rate-limit fijo puede funcionar como guard provisional, pero no sustituye evidencia sobre capacidad real de verificar/recuperar el cambio;
- high-frequency self-mod no se permite sólo porque pase un contador: cada activación material debe satisfacer su transaction/evidence gate;
- low-frequency self-mod no se bloquea arbitrariamente si el runtime puede demostrar autoridad, aislamiento, verificación y recovery suficientes.

## Failure matrix

Crash en write/build/activation, test timeout vivo, lock concurrente, dependency install parcial, disk full, rollback falla, schema incompatible, process restart entre activate/probe, ráfaga de cambios válidos, repeated failed edits, stale rate window y rate guard que bloquea recovery legítimo.

## Validation

Además de fault injection transaccional, probar que modificar el rate guard no permite overlap/double activation ni convierte frecuencia en sustituto de safety. Incluir escenario donde más de 10 cambios pequeños/verificados podrían ser legítimos y escenario donde un solo cambio debe bloquearse por no ser recuperable.

## Definition of Done

Fault injection demuestra que toda modificación termina en versión anterior utilizable o nueva versión verificada; no existe estado silencioso “source roto pero success”; la decisión de permitir/bloquear self-mod se apoya en authority + transactional safety + evidence, y cualquier rate-limit fijo superviviente queda explícitamente justificado/configurable en vez de presentarse como inteligencia universal.
