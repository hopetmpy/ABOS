## Objetivo

Permitir que ABOS evolucione su propio source sin que un build/test fallido deje el runtime activo roto ni se reporte success por el mero hecho de haber escrito archivos, preservando autonomía legítima mediante gates causales/transaccionales en vez de depender indefinidamente de un contador fijo de modificaciones.

## Auditoría completada antes de source

Se leyó todo el Required-Context y se siguieron producers/consumers hacia `src/agent/tools.ts`, `src/agent/loop.ts`, Policy path/command rules, `ConwayClient`, Git helpers, `RUNTIME_ROOT`, startup/runtime y tests existentes.

Hallazgos confirmados:
- `editFile()` escribe y committea active source antes de build y puede devolver `success: true` cuando build falla;
- el supuesto snapshot Git es best-effort, usa `git add -A` y puede capturar dirty state ajeno;
- `modifications` no es un journal transaccional y carece de base/candidate SHA, lifecycle, verification, activation y rollback outcome;
- `pull_upstream`, `revert_last_edit` y `reset_to_upstream` también mutan active checkout antes de verificar;
- local `exec` puede alcanzar el checkout y `write_file` puede alcanzar paths bajo HOME sin transaction gate;
- el loop normal serializa tool calls dentro de un proceso, pero `--run` no establece exclusión de self-mod entre procesos;
- existen dos rate guards incompatibles como cifras (`10/hour` policy y `20/hour` local), por lo que frecuencia no puede ser la authority de safety;
- SQLite `runTransaction`, Git sobre `RUNTIME_ROOT`, PolicyEngine causal y CI multi-plataforma son primitives a reutilizar, no duplicar.

La evidencia y comparación completa de alternativas vive en `ProjectOps/continuity/C0008.md`.

## Decisión arquitectónica

Seleccionado: **Git worktree aislado por transacción + journal/lease SQLite + candidate commit verificado + activation compare-and-swap contra base SHA + post-activation probe/recovery causal**.

No seleccionados como authority principal: direct-write con rollback best-effort, temp-file atomic rename, tree/index-only sin workspace ejecutable y copia/clone completo.

Flujo canónico:

Request/provenance → protected-scope check → durable transaction/lease → isolated worktree from exact base SHA → staged edits → dependency/supply-chain checks cuando aplique → typecheck/build/tests/adversarial checks → verified candidate commit → reconfirm active base/no conflict → persist activating intent → Git activation exacta → post-activation probe → activated/audit; ante fallo: no activation, rollback causal o `recovery_required`, nunca success ficticio.

## Invariantes

- constitution/core protection no se desactiva por self-mod;
- failure no devuelve success;
- active source nunca depende de una staging incompleta;
- transaction record distingue al menos proposed/staged/verifying/verified/activating/activated y failure/rolled_back/recovery_required;
- secrets/runtime state no se copian al repo/worktree;
- una lease durable impide double activation entre procesos y es reconciliable tras crash;
- activation sólo ocurre si el active checkout sigue correspondiendo al base SHA esperado y no requiere destruir drift ajeno;
- rollback sólo actúa cuando ownership causal del cambio está demostrado;
- `edit_own_file`, upstream/revert/reset y cualquier ruta local que muta `RUNTIME_ROOT` no pueden conservar garantías incompatibles;
- un rate-limit fijo puede funcionar como señal/guard configurable, pero no sustituye aislamiento, verification ni recovery y no puede bloquear recovery legítimo;
- high-frequency self-mod no se permite sólo porque pase un contador: cada activación material satisface su transaction/evidence gate;
- low-frequency self-mod no se bloquea arbitrariamente si authority, isolation, verification y recovery están demostrados;
- no se crea segunda Git/DB/Policy/Capability authority ni se absorben P-013/P-014/P-015/P-017.

## Failure matrix

Crash en workspace/write/build/activation/post-probe; test timeout vivo; lock concurrente/multiproceso; dependency install parcial; disk full; rollback falla; schema incompatible; restart entre activating/activation/probe; stale base por cambio externo; ráfaga de cambios válidos; repeated failed edits; stale rate window; rate guard que bloquea recovery legítimo.

## Validation

1. Journal/lease transitions y migration schema con rollback DB.
2. Candidate isolation: build/test failure no toca active source.
3. Stale-base/conflict no hace reset ni borra trabajo ajeno.
4. Crash/restart en cada durable boundary reconcilia base/candidate/other sin redispatch ciego.
5. Post-probe failure revierte sólo con ownership causal; rollback failure queda `recovery_required`.
6. Concurrencia multiproceso no produce double activation.
7. Más de 10 cambios pequeños/verificados pueden ser legítimos sin usar frecuencia como safety authority; un solo cambio no recuperable se bloquea aunque el contador esté vacío.
8. Node 22/24, Windows 22/24, full tests, security, rebrand, dependency audit, public smoke y ProjectOps Integrity.
9. P-013 evidence/correlation sigue requerida antes de cierre completo.

## Definition of Done

Fault injection demuestra que toda modificación termina en versión anterior utilizable, nueva versión verificada o `recovery_required` explícito cuando no es seguro automatizar rollback; no existe estado silencioso “source roto pero success”; no hay bypass conocido de mutación de `RUNTIME_ROOT` con garantías menores; la decisión de permitir/bloquear self-mod se apoya en authority + transactional safety + evidence, y cualquier frequency guard superviviente queda explícitamente justificado/configurable en vez de presentarse como inteligencia universal.
