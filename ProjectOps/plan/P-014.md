# P-014 — Consolidar Capability Fabric canónico y lifecycle de capacidades

State: PLANIFICADO
Priority: CRÍTICA

Required-Context:

Dependencies: P-008, P-009, P-010, P-013.

## Objetivo

Convertir las capacidades de ABOS en una autoridad extensible que represente qué puede hacer, con qué inputs/outputs/effects/permisos/coste/entorno/provenance/evidencia y estado operativo, reutilizando el registry/resolver existente en vez de crear otro sistema paralelo.

## Estado observado

ABOS ya posee `src/capabilities/` y semántica discover/acquire/compose/construct. La auditoría indica que matching y verificación todavía pueden ser demasiado lexicales/superficiales y que existen rutas de tools/install fuera de una sola lifecycle authority.

## Arquitectura objetivo

Capability descriptor abierto con identidad estable y metadata evolutiva: contracts I/O, effects, permissions, required environment/resources, cost/latency/reliability observations, provenance, dependencies, verifier/probe, lifecycle state y version compatibility. El resolver debe poder comparar/componer sin una allowlist cerrada de tipos de negocio.

## Invariantes

- no segundo CapabilityRegistry;
- capability instalada no equivale a verified;
- matching semántico puede usar modelos/skills, pero la ejecución final exige contratos verificables;
- permissions/effects nunca se infieren sólo del nombre;
- capability no disponible no prueba objetivo imposible.

## Plan técnico

1. inventariar registries/executors/loaders de tools/skills/MCP;
2. definir autoridad y adapters de compatibilidad;
3. extender descriptor/lifecycle sólo donde falte evidencia;
4. integrar verifier/probe y degradación;
5. persistir estado necesario sin duplicar estado primario;
6. conectar resolver con P-018 environments y P-017 acquisition.

## Ataques

Schema incompatible, capability desaparece, versión cambia, probe falso positivo, permissions cambian, composición circular, dependency missing, duplicate identity, restart.

## Definition of Done

Una necesidad puede resolverse contra capabilities existentes con contratos/evidencia suficientes; estado verified/degraded/unavailable sobrevive restart y no depende de listas arbitrarias ni de install success.
