## Objetivo

Convertir las capacidades de ABOS en una autoridad extensible que represente qué puede hacer, con qué inputs/outputs/effects/permisos/coste/entorno/provenance/evidencia y estado operativo, reutilizando el registry/resolver existente en vez de crear otro sistema paralelo.

## Estado observado

ABOS ya posee `src/capabilities/` y semántica discover/acquire/compose/construct. La auditoría demostró que el lifecycle en memoria no satisfacía restart y que el gate de `use_existing` todavía puede ser demasiado lexical/superficial para contratos ejecutables.

## Arquitectura objetivo

Capability descriptor abierto con identidad estable y metadata evolutiva: contracts I/O, effects, permissions, required environment/resources, cost/latency/reliability observations, provenance, dependencies, verifier/probe, lifecycle state y version compatibility. El resolver debe poder comparar/componer sin una allowlist cerrada de tipos de negocio.

## Invariantes

- no segundo CapabilityRegistry;
- capability instalada no equivale a verified;
- matching semántico puede usar modelos/skills, pero la ejecución final exige contratos verificables;
- permissions/effects nunca se infieren sólo del nombre;
- capability no disponible no prueba objetivo imposible;
- P-014 no absorbe P-017 acquisition/composition/construction ni P-018 environment/resource selection.

## Plan técnico

1. inventariar registries/executors/loaders de tools/skills/MCP;
2. definir autoridad y adapters de compatibilidad;
3. extender descriptor/lifecycle sólo donde falte evidencia;
4. integrar verifier/probe y degradación;
5. persistir estado necesario sin duplicar estado primario;
6. endurecer contratos del resolver y mantener adapters limpios hacia P-017/P-018.

## Ataques

Schema incompatible, capability desaparece, versión cambia, probe falso positivo, permissions cambian, composición circular, dependency missing, duplicate identity, restart, substring accidental, budget desconocido y authority ausente.

## Definition of Done

Una necesidad puede resolverse contra capabilities existentes con contratos/evidencia suficientes; estado verified/degraded/unavailable sobrevive restart y no depende de listas arbitrarias ni de install success.

## Auditoría material y decisión

### Hallazgos demostrados

- `src/capabilities/model.ts` ya posee estados abiertos y sólo `verified_available` acredita execution readiness; legacy `available=true` se degrada conservadoramente a `discovered_unverified`.
- `CapabilityRegistry` ya normaliza claims, proyecta Environment evidence y evita promover tools/skills nominales a VERIFIED.
- antes de v19, `runAgentLoop()` recreaba un registry sólo en memoria y verified/degraded/unavailable no sobrevivían restart.
- schema v18 poseía `evidence_events` sólo como correlación cross-domain; no era state store de capability.
- `skills/loader.ts` vuelve a comprobar bin/env requirements y `installed_tools`/skills persisten inventario, pero inventory enabled/install success no es runtime readiness.
- MCP configurado permanece `configured_unverified` y runtime-disabled: P-015 sigue siendo su owner.
- Environment providers producen snapshots/evidence; P-018 sigue siendo owner de resource/environment selection.
- matching actual usa texto/substrings principalmente; es útil para discovery pero no basta como contrato de ejecución cuando permissions/effects/contracts son relevantes.

### Hipótesis falsadas de arquitectura base

- `NO_CHANGE`: FALSADA — el lifecycle no sobrevivía restart y el DoD lo exige.
- `REPLACE`: FALSADA — registry/model/resolver existentes ya contienen semántica correcta de open-world/runtime truth; reemplazarlos crearía regresión y autoridad paralela.
- `PARALLEL_REGISTRY`: DESCARTADA por invariante de authority única.

### Decisión base seleccionada

`EXTEND_IN_PLACE / UNIFY_AUTHORITY / DURABLE_LIFECYCLE`.

1. conservar `CapabilityRegistry` como única facade/authority de dominio;
2. añadir backing SQLite versionado para lifecycle, no una segunda registry authority;
3. hidratar desde ese backing al arrancar y persistir transiciones evidence-backed;
4. adaptar tool/skill/environment inventories al mismo registry; inventory/acquisition nunca eleva por sí sola a VERIFIED;
5. introducir definition/version fingerprint para que una capability modificada no herede ciegamente verificación;
6. proporcionar transición/probe explícita para VERIFIED/DEGRADED/UNAVAILABLE con authority + evidence + observedAt;
7. enriquecer descriptor de forma abierta, sin business allowlists;
8. permitir matching lexical/semántico como discovery, pero exigir state/evidence y contratos explícitamente solicitados antes de `use_existing`;
9. preservar P-015 MCP, P-017 acquisition/construction y P-018 environment/resource selection como owners separados conectados por adapters.

## Segunda unidad — contracts y execution gate

### Evidencia observada

- `CapabilityResolver.use_existing` todavía puede derivar de substring lexical sobre campos descriptivos.
- budget explícito permite hoy `estimatedCostCents == null`; eso no demuestra que el ceiling se cumpla.
- `register()` puede conservar `verified_available` con evidence+observedAt sin exigir authority, mientras `recordProbe()` sí la exige.
- `CapabilityType` permanece cerrado aunque el proyecto exige mundo abierto.
- `requiredPermissions` existe en `CapabilityRequest` pero no se expone por `resolve_capability`.
- faltan campos contractuales explícitos de `provides`, `effects`, dependencies y version/compatibility.
- `requirements` está usado históricamente como alias de capability ofrecida; reinterpretarlo como dependency rompería producers existentes.
- P-017 es owner del pipeline ejecutable de discover/acquire/compose/construct; P-018 es owner de environment/resource selection y ya demuestra semántica fail-closed para budget unknown/incomplete.

### Hipótesis discriminadas

- `NO_CHANGE`: FALSADA.
- `RESOLVER_ONLY`: FALSADA.
- `FULL_DESCRIPTOR_REWRITE`: FALSADA.
- `MOVE_COMPOSITION_OR_ENV_SELECTION_INTO_P014`: FALSADA.
- `EXTEND_CONTRACT_SURFACE_AND_HARDEN_EXECUTION_GATE`: CONFIRMADA.

### Decisión — DECISION_READY

`EXTEND_MODEL / HARDEN_RESOLUTION / REUSE_P018_BUDGET_SEMANTICS / PRESERVE_P017_P018_OWNERSHIP`.

Secuencia autorizada:

1. conservar un vocabulario `CORE_CAPABILITY_TYPES` documentado pero hacer `CapabilityType` abierto;
2. añadir aditivamente `provides`, `effects`, `dependencies`, `version`, `compatibility`; mantener `requirements` como alias legacy declarado;
3. ampliar request con restricciones explícitas de inputs/outputs/effects/compatibility;
4. exigir authority + evidence + observedAt para aceptar `verified_available`;
5. permitir `use_existing` sólo por contrato declarado exacto, permissions/I/O/effects/compatibility satisfechos, dependencies VERIFIED y budget explícito con coste conocido ≤ ceiling;
6. conservar description/substring matching únicamente para discovery/probe/compose-candidate;
7. incluir campos contractuales de definición en fingerprint durable;
8. exponer `requiredPermissions` y restricciones contractuales en `resolve_capability`;
9. no ejecutar acquisition/composition/construction ni environment selection dentro de esta unidad.

Validación adversarial obligatoria: substring accidental, authority ausente, budget con coste desconocido, permission/effect/input/output faltante, dependency no verificada, contract/version change tras restart, tipo futuro no enumerado y composición lexical incapaz de elevarse a `use_existing`.
