## Objetivo

Permitir a ABOS actuar sobre una computadora autorizada mediante primitivas generales y verificables, sin obligarlo a depender de un MCP para cada acción ni a mover mouse cuando existe una interfaz estructurada mejor.

## Subtracks objetivo

1. Local filesystem/process/shell: read/write/move, process lifecycle, command execution, cwd/env y cancellation con policy.
2. Application/OS integration: procesos/apps, clipboard/notifications cuando exista API portable/segura.
3. Browser: navegación y automatización estructurada preferentemente por DOM/CDP/Playwright-equivalente; uploads/downloads y session handling bajo autorización.
4. GUI/accessibility/input: screen/window/accessibility tree y mouse/keyboard sólo cuando una interfaz más semántica no existe.

## Jerarquía de ejecución preferida

API/CLI estructurada → browser DOM/accessibility → GUI visual/input. La preferencia optimiza fiabilidad/coste, no crea fallback silencioso: cambiar de frontera es una nueva ruta explícita.

## Invariantes

- host/executor explícito; no confundir local con Conway/AWS/child;
- filesystem scope y destructive effects pasan policy;
- credentials/sessions se manejan por stores autorizados, no logs/prompts;
- upload/download verifica outcome;
- headless/GUI ausencia es UNAVAILABLE, no IMPOSSIBLE.

## Preguntas

¿Qué primitivas ya existen en agent/tools/environments? ¿Qué debe ser capability versus environment operation? ¿Cómo soportar Windows/Linux sin bifurcar semántica central? ¿Cómo recuperar browser/process tras restart?

## Validation

E2E local: crear/editar archivo, ejecutar proceso, abrir/navegar browser, download/upload controlado y verificar resultado; GUI/accessibility sólo donde el runner/entorno lo permita. Failure/cancel/restart incluidos.

## Definition of Done

ABOS posee una ruta general para operar la computadora autorizada y puede seleccionar la interfaz menos frágil disponible, con evidence/provenance/policy y sin claims de GUI/browser cuando el host no la ofrece.
