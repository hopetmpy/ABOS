## Objetivo

Cuando ABOS detecte un capability gap, permitir una búsqueda adaptativa y autorizada: reutilizar → descubrir → adquirir → componer → construir → probar → registrar, en vez de estar limitado a tools preinstaladas o instalar ciegamente paquetes.

## Fuentes candidatas abiertas

MCP, CLI, API/SDK, package Node/Python u otro runtime disponible, OS capability, service externo, skill existente o adapter construido por ABOS. Esta lista es ejemplo, no allowlist exhaustiva.

## Acquisition lifecycle

NEED → CANDIDATES → provenance/risk/cost evaluation → ACQUIRE in quarantine/staging → configure without leaking secrets → functional probe → register VERIFIED or mark DEGRADED/REJECTED → observe real use → retain/upgrade/retire.

## Reglas

- preferir capacidad existente/estándar antes de escribir otra;
- package installed != capability usable;
- no descargar/ejecutar código no confiable sin policy/supply-chain evaluation;
- adquisición con coste requiere treasury/authorization;
- construction usa P-012 transactional self-mod;
- cada intento fallido reduce espacio de búsqueda.

## Validation

Escenario E2E donde una tarea requiere capability ausente: ABOS detecta gap, descubre candidato, lo adquiere o construye, hace probe, lo registra, lo usa y verifica outcome. Escenarios negativos: paquete malicioso/incompatible, auth ausente, coste excedido, probe falla.

## Definition of Done

Un capability gap legítimo no obliga a hardcode manual: existe un pipeline reusable y auditable que puede terminar en VERIFIED, UNAUTHORIZED, UNAVAILABLE o NO_DISCOVERED sin inventar éxito.
