## Objetivo

Consolidar Local, Conway, AWS y futuros environments bajo una sola semántica de capability/resource/lifecycle/continuity, preservando que provider ID es dato y que un resource failure no implica provider/world failure.

## Estado observado

ABOS ya posee EnvironmentRegistry, selector, lifecycle, mobility, resource stores y providers Local/Conway/AWS. Este P es principalmente de reconciliación/fortalecimiento: no crear otro environment system.

La auditoría P-018 confirma que lifecycle, mobility y resource stores ya son provider-neutral y preservan failure scope/resource ownership. El gap material está en la frontera de capability-readiness: Environment todavía puede elevar `available: true` y coincidencias textuales a elegibilidad de ejecución, mientras P-014 define `verified_available` como único estado execution-ready.

## Arquitectura objetivo

Requirements describen capabilities/operations/permisos/budget/continuity; providers inspeccionan availability y estiman coste/reliability cuando pueden; selector conserva UNKNOWN; resources tienen identidad/lifecycle/evidence; migration/recovery mueve sólo lo que posee una authority clara.

P-018 no crea otra capability authority. Reutiliza la semántica P-014 para decidir cuándo una capability puede sostener elegibilidad, y deja provider-specific checks como restricciones adicionales, nunca como elevación de una capability no verificada.

## Invariantes

- no silent executor fallback;
- resource-specific failure scope;
- explicit cost coverage bajo budget;
- state/artifacts/identity distinguen checkout, `~/.abos`, remote resource y child;
- preferred environment no puede saltar blockers de auth/policy/budget;
- `available` o discovery textual no equivalen a execution-ready;
- provider authentication/credits no prueban por sí solos acceso funcional a cada service capability;
- provider IDs siguen siendo runtime data, no allowlist central.

## Hipótesis discriminadas

- `NO_CHANGE`: FALSADA — selector/providers mantienen una semántica de readiness más débil que P-014.
- `CREATE_SECOND_ENVIRONMENT_SYSTEM`: RECHAZADA — registry/lifecycle/mobility/resource fabric existentes ya cubren ownership estructural.
- `EXTEND_EXISTING_ENVIRONMENT_FABRIC`: ACEPTADA.
- `UNIFY_CAPABILITY_READINESS_WITH_P014`: ACEPTADA.
- `MARK_ALL_PROVIDER_CAPABILITIES_VERIFIED_AFTER_AUTH`: RECHAZADA — auth/credits no demuestran cada operación/service.

## Primera unidad

1. Unificar matching/elegibilidad de capability con P-014: sólo `verified_available` puede satisfacer execution requirements y el match usa contract channels, no descripción libre.
2. Reconciliar descriptors Local/Conway/AWS para no inventar verificación: capabilities funcionalmente demostradas pueden expresar evidence/state; service capabilities no probadas permanecen discovered/probed/unavailable según evidencia real.
3. Hacer que `environment_capabilities` exponga state/authority/evidence/provides en vez de colapsar runtime truth a boolean `available`.
4. Agregar regresiones que prueben que legacy `available:true`, STS/credits y fuzzy description no saltan P-014 readiness.

## Preguntas

¿Hay operaciones duplicadas entre capability y environment? ¿Qué parte de AWS/Conway sigue E1-E4 versus LIVE? ¿Cómo representar GPU/browser/desktop/long-running resources sin listas centrales?

## Validation

Selection y failover por replanning entre environments compatibles; resource failure scoped; continuity/restart; budget unknown; provider unavailable; artifact portability; tests con injected providers y LIVE sólo bajo P-005.

## Definition of Done

Una tarea puede expresar requirements abiertos y obtener un environment/resource elegible con evidencia, o una explicación UNKNOWN/UNAUTHORIZED/UNAVAILABLE útil para replanning, sin hardcode central de providers.
