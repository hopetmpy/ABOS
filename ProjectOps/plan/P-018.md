## Objetivo

Consolidar Local, Conway, AWS y futuros environments bajo una sola semántica de capability/resource/lifecycle/continuity, preservando que provider ID es dato y que un resource failure no implica provider/world failure.

## Estado observado

ABOS ya poseía EnvironmentRegistry, selector, lifecycle, mobility, resource stores y providers Local/Conway/AWS. P-018 fue una fase de reconciliación/fortalecimiento: no se creó otro environment system.

La auditoría confirmó que lifecycle, mobility y resource stores ya eran provider-neutral y preservaban failure scope/resource ownership. El gap material estaba en la frontera de capability-readiness: Environment podía elevar `available: true` y coincidencias textuales a elegibilidad de ejecución, mientras P-014 define `verified_available` como único estado execution-ready.

## Arquitectura integrada

Requirements describen capabilities/operations/permisos/budget/continuity; providers inspeccionan availability y estiman coste/reliability cuando pueden; selector conserva UNKNOWN; resources tienen identidad/lifecycle/evidence; migration/recovery mueve sólo lo que posee una authority clara.

P-018 no creó otra capability authority. Reutiliza la semántica P-014 para decidir cuándo una capability puede sostener elegibilidad, y deja provider-specific checks como restricciones adicionales, nunca como elevación de una capability no verificada.

## Resultado implementado

- `EnvironmentSelector` exige capability contract matching y estado `verified_available` para elegibilidad de ejecución.
- `EnvironmentRegistry.findForCapability()` aplica la misma semántica de readiness y deja de usar discovery textual como prueba funcional.
- `environment_capabilities` proyecta state, provides, authority y evidence en vez de colapsar runtime truth a `available`.
- Local publica readiness respaldada por probes/runtime evidence para las capabilities que realmente puede demostrar.
- AWS CLI + STS prueban provider/account availability, no disponibilidad funcional de EC2/SSM/Lambda/ECS/S3/SQS/DynamoDB/RDS.
- Conway credits prueban provider/account availability, no readiness funcional automática de sandbox/inference.
- Fixtures heredadas de mobility/tooling fueron reconciliadas para declarar explícitamente evidencia `verified_available` cuando el test realmente modela ejecución disponible.
- Se preservó el fabric provider-neutral existente; no se introdujo allowlist central ni lifecycle paralelo.

## Invariantes preservados

- no silent executor fallback;
- resource-specific failure scope;
- explicit cost coverage bajo budget;
- state/artifacts/identity distinguen checkout, `~/.abos`, remote resource y child;
- preferred environment no puede saltar blockers de auth/policy/budget;
- `available` o discovery textual no equivalen a execution-ready;
- provider authentication/credits no prueban por sí solos acceso funcional a cada service capability;
- provider IDs siguen siendo runtime data, no allowlist central.

## Hipótesis discriminadas

- `NO_CHANGE`: FALSADA — selector/providers mantenían una semántica de readiness más débil que P-014.
- `CREATE_SECOND_ENVIRONMENT_SYSTEM`: RECHAZADA — registry/lifecycle/mobility/resource fabric existentes ya cubrían ownership estructural.
- `EXTEND_EXISTING_ENVIRONMENT_FABRIC`: ACEPTADA e implementada.

- `MARK_ALL_PROVIDER_CAPABILITIES_VERIFIED_AFTER_AUTH`: RECHAZADA — auth/credits no demuestran cada operación/service.
