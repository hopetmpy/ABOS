## Objetivo

Consolidar Local, Conway, AWS y futuros environments bajo una sola semántica de capability/resource/lifecycle/continuity, preservando que provider ID es dato y que un resource failure no implica provider/world failure.

## Estado observado

ABOS ya posee EnvironmentRegistry, selector, lifecycle, mobility, resource stores y providers Local/Conway/AWS. Este P es principalmente de reconciliación/fortalecimiento: no crear otro environment system.

## Arquitectura objetivo

Requirements describen capabilities/operations/permisos/budget/continuity; providers inspeccionan availability y estiman coste/reliability cuando pueden; selector conserva UNKNOWN; resources tienen identidad/lifecycle/evidence; migration/recovery mueve sólo lo que posee una authority clara.

## Invariantes

- no silent executor fallback;
- resource-specific failure scope;
- explicit cost coverage bajo budget;
- state/artifacts/identity distinguen checkout, `~/.abos`, remote resource y child;
- preferred environment no puede saltar blockers de auth/policy/budget.

## Preguntas

¿Hay operaciones duplicadas entre capability y environment? ¿Qué parte de AWS/Conway sigue E1-E4 versus LIVE? ¿Cómo representar GPU/browser/desktop/long-running resources sin listas centrales?

## Validation

Selection y failover por replanning entre environments compatibles; resource failure scoped; continuity/restart; budget unknown; provider unavailable; artifact portability; tests con injected providers y LIVE sólo bajo P-005.

## Definition of Done

Una tarea puede expresar requirements abiertos y obtener un environment/resource elegible con evidencia, o una explicación UNKNOWN/UNAUTHORIZED/UNAVAILABLE útil para replanning, sin hardcode central de providers.
