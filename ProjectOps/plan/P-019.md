## Objetivo

Preservar la arquitectura ya existente de conexión/adapters/model registry/router y hacer que ABOS pueda elegir dinámicamente entre modelos compatibles del provider/conexión activa según dificultad, coste, latencia, evidencia y reasoning effort, sin restringirlo a un modelo fijo ni saltar silenciosamente entre providers.

## Decisión vigente

La conexión principal actual puede ser Codex OAuth; dentro de Codex se conservan discovery, selección manual, hot switching y fallback compatible. Si en el futuro se añade Anthropic/u otro provider, entra por adapter y expone su catálogo; no se preconstruye soporte ficticio ahora.

Separación obligatoria: connection/auth method != provider/runtime != model != reasoning effort != capability/tools.

## Problemas a auditar

- baseline estático no debe invalidar modelos dinámicamente descubiertos;
- provider registries legacy/paralelos deben reconciliarse antes de extender;
- fallback sólo puede usar rutas compatibles/autorizadas y no multiplicar timeouts;
- modelos pequeños no garantizan menos tokens; contexto/reasoning/output también cuentan.

## Adaptive inference objetivo

Primero: ¿necesita inferencia? Si sí: mantener session/model affinity razonable; escalar reasoning antes o junto con modelo según evidencia; elegir modelo dentro del provider activo; bajar capacidad cuando la tarea lo permita; manual lock/ceiling siempre respetable.

## Telemetría

Registrar model, provider, reasoning, input/output tokens, latency, cost observed/estimated, retries y outcome evidence para P-025 Cognitive Cost, sin crear otro spend ledger.

## Definition of Done

Catálogo dinámico gobierna opciones compatibles; usuario puede fijar modelo o modo adaptativo; ABOS puede escalar/deescalar dentro del provider activo con policy/budget y no existe cross-provider switch silencioso.
