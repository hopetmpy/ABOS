## Objetivo

Preservar la arquitectura ya existente de conexión/adapters/model registry/router y hacer que ABOS pueda elegir dinámicamente entre modelos compatibles del provider/conexión activa según dificultad, coste, latencia, evidencia y reasoning effort, sin restringirlo a un modelo fijo ni saltar silenciosamente entre providers.

## Hallazgos verificables

1. `ModelRegistry.initialize()` trata providers del baseline estático como si el baseline poseyera su lifecycle y puede deshabilitar un modelo dinámico del mismo provider sólo porque no está en la lista estática.
2. El test `dynamic-model-provider-preservation.test.ts` protege providers nuevos, pero actualmente espera que un modelo OpenAI no incluido en baseline se deshabilite; esa expectativa contradice el objetivo P-019 de catálogo dinámico abierto.
3. `InferenceRouter` ya ofrece la frontera correcta para compatibilidad/budget/timeout/evidence y debe extenderse, no duplicarse.
4. Codex ya posee catálogo dinámico, metadata de reasoning effort y runtime real; el adaptive layer debe consumir esas capacidades sin inventar un catálogo paralelo.
5. El legacy `ProviderRegistry` mantiene catálogo/precios/fallback propios y `UnifiedInferenceClient.chat()` puede continuar silenciosamente hacia otro provider ante errores retryable. Eso contradice `BOUNDARY_SWITCH_REQUIRES_REPLAN` y la Definition of Done P-019.
6. Antes de retirar el legacy path hay que demostrar sus consumers reales; existencia de código o tests no prueba que sea runtime authority activa.

## Hipótesis discriminadas

- H0 `NO_CHANGE`: FALSADA — existe conflicto de lifecycle para modelos dinámicos same-provider y una ruta legacy con cross-provider fallback silencioso.
- H1 `EXTEND_EXISTING_CONNECTION_MODEL_FABRIC`: ACEPTADA.
- H2 `CREATE_NEW_ADAPTIVE_PROVIDER_MANAGER`: RECHAZADA — duplicaría registries/router/connection authority.
- H3 `RETIRE_OR_CONSTRAIN_LEGACY_PROVIDER_REGISTRY_AFTER_CONSUMER_AUDIT`: ACEPTADA provisionalmente; no se borra nada hasta verificar consumers/migración.
- H4 `STATIC_BASELINE_OWNS_PROVIDER_MODEL_LIFECYCLE`: FALSADA — baseline debe sembrar defaults, no retirar dinámicos no observados por su propia authority.
- H5 `RETRYABLE_MODEL_FAILURE_ALLOWS_SILENT_CROSS_PROVIDER`: FALSADA — provider/connection boundary cambia sólo mediante replan/authority explícita.
- H6 `ADAPTIVE_INFERENCE_BELONGS_IN_EXISTING_ROUTER_PLUS_ADAPTER_METADATA`: ACEPTADA.

## Primera unidad autorizada

1. Corregir `ModelRegistry.initialize()` para que el baseline estático sea seed/config inicial y no deshabilite modelos dinámicos same-provider.
2. Actualizar regresiones para demostrar preservación de modelo dinámico del mismo provider y conservar upsert/refresco del baseline sin falsa retirement authority.
3. Auditar consumers reales de `ProviderRegistry`/`UnifiedInferenceClient`; sólo después decidir migración, compatibilidad o retiro.
4. Extender candidate collection/routing para que el catálogo dinámico compatible participe dentro de la conexión/provider activa, respetando manual lock, policy y budget.
5. Introducir adaptive reasoning/model choice sobre las authorities existentes; no crear segundo provider manager ni otro spend ledger.

## Decisión vigente

La conexión principal actual puede ser Codex OAuth; dentro de Codex se conservan discovery, selección manual, hot switching y fallback compatible. Si en el futuro se añade Anthropic/u otro provider, entra por adapter y expone su catálogo; no se preconstruye soporte ficticio ahora.

Separación obligatoria: connection/auth method != provider/runtime != model != reasoning effort != capability/tools.

## Adaptive inference objetivo

Primero: ¿necesita inferencia? Si sí: mantener session/model affinity razonable; escalar reasoning antes o junto con modelo según evidencia; elegir modelo dentro del provider activo; bajar capacidad cuando la tarea lo permita; manual lock/ceiling siempre respetable.

## Telemetría

Registrar model, provider, reasoning, input/output tokens, latency, cost observed/estimated, retries y outcome evidence para P-025 Cognitive Cost, reutilizando P-013 y sin crear otro spend ledger.

## Límites de claim

- CI/E3 no prueba conectividad/provider LIVE E5 ni coste económico LIVE E6.
- No se cambia de provider por retry interno equivalente.
- Un catálogo dinámico observado no implica que todos sus modelos estén autorizados/compatibles con la conexión activa.
- Un modelo pequeño no se considera automáticamente más barato en coste total sin evidencia de tokens/context/reasoning/output.

## Definition of Done

Catálogo dinámico gobierna opciones compatibles; usuario puede fijar modelo o modo adaptativo; ABOS puede escalar/deescalar dentro del provider activo con policy/budget y no existe cross-provider switch silencioso.
