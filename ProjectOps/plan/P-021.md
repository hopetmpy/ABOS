## Objetivo

Permitir que ABOS convierta experiencias repetibles en procedimientos reutilizables, versionados y verificables, reduciendo razonamiento/tokens sin cristalizar errores como conocimiento procedural.

## Modelo integrado

Experience/evidence → pattern candidate → candidate skill → applicability/inputs/preconditions → replay/validation → ACTIVE → usage observations → evolve/degrade/deprecate/fallback/rollback.

Skills son procedimientos runtime; memory conserva hechos/episodios/procedures aprendidos; Capability Fabric conserva execution readiness; Evidence Fabric conserva correlation/provenance.

## Arquitectura decidida e integrada

1. **REUSE** `src/skills/registry.ts`, loader/format y tool/policy path existentes. No segundo registry.
2. **REUSE** procedural memory como learning substrate; no convertirlo en skill authority.
3. **CREATE additive persistence v20** porque `skills(name PK)` + `INSERT OR REPLACE` no podía preservar versiones/rollback y ni modifications, P-012 self-mod journal ni Evidence Fabric eran semánticamente equivalentes.
4. Authority durable:
   - `skill_versions`: definition/version/parent/lifecycle/contracts/applicability/verification/provenance/evidence/hash/timestamps;
   - `skill_evaluations`: replay/validation/usage observations append-only referidas a evidence real.
5. `skills` permanece **runtime projection compatible**, seleccionada por la version authority; no segunda fuente de truth histórica.
6. Capability Fabric sigue siendo **única authority de execution readiness**. Evolved skill descriptors incorporan version/dependencies/permissions/effects/environment/compatibility/I/O para que el fingerprint cambie cuando cambia la definición.
7. Promotion usa evidence IDs existentes y dependencies execution-ready. Una critical skill exige al menos dos success observations independientes; verification policy puede exigir más, nunca menos para critical.
8. lifecycle: candidate → validated/active → degraded/deprecated/superseded; rollback sólo a una versión previamente validada con evidence.
9. loader/legacy registry no pueden sobrescribir o retirar silenciosamente una skill gestionada por evolution.
10. main loop refresca inventory desde DB; evolved instructions sólo entran al prompt si la capability correspondiente permanece execution-ready. Legacy skills no gestionadas conservan compatibilidad.

## Invariantes satisfechas

- candidate != active != verified capability;
- una ejecución exitosa aislada no basta para promover una skill crítica;
- skill no eleva permisos ni oculta tools/effects/dependencies;
- versiones/provenance/rollback sobreviven restart;
- failure/degrade actualiza applicability/lifecycle y no borra history;
- inventory/enabled no equivale a `verified_available`;
- no segunda authority para procedural memory, capability readiness, policy o evidence;
- secrets/credentials no se materializan como contenido/provenance de skill;
- projection + lifecycle DB state se actualizan transaccionalmente y nunca quedan dos active versions;
- definition/version change invalida evidence obsoleta mediante capability fingerprint;
- UNKNOWN/unavailable dependency no se convierte en success.
