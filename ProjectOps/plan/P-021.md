La brecha material no es “crear skills desde cero”: es versionar, validar, promover/degradar y recuperar skills desde experiencia verificable sin duplicar esas authorities.

## Objetivo

Permitir que ABOS convierta experiencias repetibles en procedimientos reutilizables, versionados y verificables, reduciendo razonamiento/tokens sin cristalizar errores como conocimiento procedural.

## Modelo objetivo

Experience/evidence → pattern candidate → candidate skill → applicability/inputs/preconditions → sandbox/replay validation → ACTIVE → usage observations → evolve/deprecate/fallback. Skills son procedimientos; memory conserva hechos/episodios y Capability Fabric conserva lo que puede ejecutarse.

## Invariantes

- una ejecución exitosa aislada no basta para promover una skill crítica;
- skill no puede elevar permisos ni ocultar tools/effects subyacentes;
- cada skill declara required capabilities/environment y verification method;
- versiones conservan provenance y rollback;
- failure actualiza applicability, no borra ciegamente la skill;
- inventory/enabled no equivale a `verified_available`;
- no se crea una segunda authority para procedural memory, capability readiness, policy o evidence;
- secrets/credentials no se materializan como contenido/provenance de skill.

## Estado observado al activar

- `skills` es un snapshot mutable por nombre; `upsertSkill()` usa `INSERT OR REPLACE`, por lo que no preserva versiones previas ni rollback;
- `src/skills/registry.ts` ya instala/crea/deshabilita skills y no debe duplicarse;
- `src/skills/loader.ts` ya revalida requisitos runtime y trust boundary tras restart;
- `ProceduralMemoryManager` ya posee steps + success/failure counts y debe reutilizarse como learning substrate, no como skill registry;
- `CapabilityRegistry.ingestSkills()` trata inventory habilitado como `discovered_unverified`; readiness pertenece a Capability Fabric y sólo evidence-backed `verified_available` es ejecutable;
- `CapabilityDescriptor` ya soporta dependencies, permissions, effects, version, compatibility, environment, inputs/outputs y evidence;
- P-013 Evidence Fabric ya soporta provenance/correlation de lifecycle events;
- `install_skill` y self-create ya pasan por el tool/policy path normal.

## Preguntas/falsación

¿Qué loader/store/versioning ya existe? ¿Cómo evitar duplicar skills equivalentes? ¿Cuándo conviene una skill versus código/tool? ¿Cómo medir éxito sin autoevaluación circular? ¿Qué experiencias contienen secretos que no deben materializarse? ¿Puede modification/self-mod/evidence history representar rollback completo sin una authority de versión nueva? ¿Cómo mantener projection `skills` y version lifecycle atómicos?

## Validation

Crear candidate desde una tarea repetida, validar por replay, usarla en una tarea nueva, medir ahorro/resultado, degradarla ante condición inválida y recuperar versión anterior. Añadir restart/persistence, authority isolation, negative promotion y secret/provenance tests; reusar runtime-truth/hardening existentes.

## Definition of Done

ABOS puede crear/actualizar/deprecar una skill desde evidencia y reusarla con contracts y capabilities reales, sin confundir una narración procedural con una herramienta ejecutable.
