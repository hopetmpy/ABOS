## Objetivo

Dar a ABOS una representación explícita y actualizable de qué cree sobre el mundo/tarea, con evidencia, confianza opcional, temporalidad, supuestos, alternativas y condiciones de falsación, en lugar de depender sólo del texto del último prompt o de keywords.

## Auditoría y decisión

La auditoría de source/runtime encontró una authority parcial real, no un vacío arquitectónico:

- `AdaptiveStore` ya persiste `adaptive_world_facts` y `adaptive_assumptions` goal-scoped;
- `AdaptivePathEngine` produce/consume ese estado y lo proyecta mediante `buildPlannerContext()`;
- `Orchestrator` inyecta ese contexto en plan/replan y el Agent Loop instancia ese orchestrator en el runtime principal;
- Evidence Fabric ya posee correlation/provenance y la taxonomía `observation | estimate | inference | assumption | unknown`, pero explícitamente no es canonical adaptive state;
- Cognitive Fabric/`knowledge_store` no posee scope ni lifecycle equivalente para competing hypotheses/falsification.

El gap material inicial fue que `adaptive_world_facts` mantiene sólo un valor por `goalId + key`, el world state no representa múltiples beliefs competidores, no posee lifecycle general de invalidation/falsification/expiry y el planner no recibe qué hipótesis compiten ni qué las falsaría.

La auditoría posterior al primer source slice detectó además que store + consumer no bastan: ningún flujo runtime llamaba `recordBelief()`. Sin producer real, el world model sólo podía poblarse desde tests o llamadas manuales.

Ese owner puede producir la primera clase material de beliefs —viabilidad de hipótesis estratégica— sin crear callback/global ni ampliar `Orchestrator`.

## Arquitectura objetivo decidida

No crear un segundo world-model manager ni convertir Memory/Evidence/Planner en owner.

1. **Facts existentes** — `adaptive_world_facts` permanece canonical fact snapshot y compatible con P-013/existing consumers.
2. **Beliefs explícitos** — `adaptive_world_beliefs` bajo `AdaptiveStore` para múltiples claims competidores por key.
3. **Epistemic status** — semántica compatible con Evidence Fabric: `observation`, `inference`, `estimate`, `assumption`, `unknown`.
4. **Confidence** — nullable; `null` significa no calibrada/no disponible y nunca se convierte implícitamente en 0/0.5/1.
5. **Temporalidad** — `lastVerifiedAt` y `expiresAt`; un belief expirado no se presenta al planner como vigente.
6. **Lifecycle** — `active`, `invalidated`, `superseded`; stale/expired se deriva de temporalidad sin borrar evidencia histórica.
7. **Evidence/provenance** — canonical belief guarda referencias/evidence refs y falsification conditions; Evidence Fabric registra eventos referenciales correlacionados por authority ID, no una copia del canonical value.
8. **Contradicción** — una actualización puede invalidar/superseder beliefs identificados de forma transaccional; múltiples alternatives pueden coexistir cuando la evidencia no discrimina.
9. **Runtime consumer** — `PossibilitySpace` y `AdaptivePathEngine.buildPlannerContext()` proyectan beliefs vigentes, alternatives, UNKNOWN/freshness y falsification conditions al planner/replanner real.
10. **Runtime producer inicial** — `AdaptivePathEngine.selectCandidate()` materializa la hipótesis estratégica seleccionada como belief `inference` no calibrada bajo una key común de viabilidad de ruta. Repetir el mismo path no duplica el claim activo. Un failure con `terminalForPath=true` invalida ese belief usando el Evidence Fabric event del fallo como evidence ref. Failures no terminales preservan el claim como alternativa condicionada; si replan selecciona otra ruta, ambas pueden coexistir como competing hypotheses hasta que evidencia discrimine.
11. **Falsabilidad estratégica** — la condición de falsación de esa clase de belief está ligada al outcome esperado y a un failure terminal bajo condiciones materialmente equivalentes; no se inventa una probabilidad.
12. **Fronteras** — prediction-error learning queda en P-023, simulation/experiments en P-024 y strategic cognition adicional en P-025. Claims arbitrarios del planner no se incorporan a state sin un contrato estructurado/validado; P-022 no usará parsing libre del texto del planner.

## Reglas

- OBSERVED / INFERRED / ESTIMATED / ASSUMED / UNKNOWN explícitos;
- una hipótesis competidora es obligatoria ante incertidumbre material cuando exista evidencia para más de una alternativa;
- evidence contradictoria debe poder invalidar/superseder belief; no se ignora para proteger un plan;
- stale beliefs expiran del conjunto vigente sin perder historial;
- imposible requiere evidencia, no agotamiento subjetivo;
- no se crea un segundo memory/knowledge/evidence/planner authority por conveniencia;
- canonical values adaptativos no se duplican en Evidence Fabric;
- UNKNOWN permanece first-class y no equivale a false/zero;
- confidence ausente permanece `null`;
- una repetición del mismo path/source no crea beliefs duplicados;
- sólo `terminalForPath` falsifica automáticamente la viabilidad estratégica; authorization/resource/environment/capability/transient failures no se convierten en contradicción terminal por conveniencia.

## Validation requerida

- fresh/raw DB crea `adaptive_world_beliefs`; migration global/versionada V20→V21 sigue siendo requisito separado antes del cierre;
- restart/reopen conserva beliefs y lifecycle;
- dos o más beliefs activos pueden competir para una misma key;
- UNKNOWN + confidence null sobreviven round-trip;
- invalidation/supersession cambia el estado consumido y conserva historial;
- expiry excluye belief del conjunto vigente sin eliminarlo;
- Evidence Fabric correlaciona lifecycle events por authority ID y no replica canonical value;
- planner context muestra beliefs competidores y falsification conditions;
- seleccionar un path produce exactamente un strategic belief activo para ese path/source aunque se seleccione de nuevo;
- failure terminal invalida el strategic belief y referencia evidence real del fallo;
- failure no terminal no invalida falsamente el strategic belief;
- un replan tras failure no terminal puede dejar dos strategic hypotheses competidoras vigentes para la misma key;
- existing fact API/P-013 correlation contract permanece compatible;
- tests negativos/adversariales, typecheck, build, full test suite, security/ProjectOps y CI exact-head.
