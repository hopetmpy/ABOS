## Objetivo

Maximizar resultado útil por recurso cognitivo gastado, no simplemente minimizar tokens. Antes de inferencia, ABOS debe considerar memoria, skill, cálculo, código, retrieval o simulación; si requiere modelo, elegir contexto/model/reasoning adecuados dentro de la frontera autorizada.

## Decision ladder orientativa

1. cache/memory/known verified fact;
2. deterministic computation/code/tool;
3. validated skill/procedure;
4. simulation/replay;
5. inference con modelo/effort adecuado;
6. escalamiento cuando evidencia justifica mayor capacidad.

No es una lista rígida: el controller compara coste, latency, uncertainty, reversibility e information gain.

## Métricas

Tokens, latency, model/provider, monetary cost, context bytes/tokens, retry cost, success evidence, rework y reusable learning created. Un modelo “barato” que genera múltiples retries puede costar más globalmente.

## Learning

Aprender por task class qué combinación produce mejor outcome/cost; preservar manual model lock, budget ceilings y provider boundary.

## Auditoría requerida

Antes de crear una nueva authority, contrastar el runtime actual y demostrar qué responsabilidad no está ya cubierta por:
- inference router/model registry/budget ledger;
- Cognitive Fabric y context/retrieval budgets;
- skill registry/evolution;
- Prediction Learning/Adaptive Path/Evidence;
- Simulation Workspace;
- state/database canónicos.

El objetivo no autoriza duplicar estos owners. Si el delta requiere un controller, debe ser de decisión/orquestación y delegar ejecución/persistencia especializada a las authorities existentes.

## Definition of Done

ABOS puede justificar por qué llamó o no llamó a un modelo, escalar/deescalar compute con evidencia y medir savings sin degradar success/quality de forma silenciosa.
