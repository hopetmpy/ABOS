## Origen y problema

El roadmap ABOS previo a P-007 separaba una capacidad de `Branching Memory + progressive disclosure`: conocimiento durable amplio, ramas contextuales activas/dormidas, expansión bajo necesidad, checkpoints y reactivación causal. P-007 compactó memory/context/knowledge/activation principalmente en P-020 sin dejar una matriz explícita de equivalencia.

La auditoría histórica de 2026-09-24 encontró cobertura **parcial**, no ausencia total:
- `ContextManager` y retrieval ya controlan working context y presupuesto;
- `CompressionEngine` implementa una cascada progresiva de cinco stages;
- stage 4 genera checkpoint/reset, conserva summary, goals/tasks y rehidrata knowledge;
- P-020 ya integró cinco memory tiers, knowledge activation y restart durable.

No quedó demostrada equivalencia para el lifecycle histórico de ramas contextuales: identidad durable de branch, active/dormant state, parentesco/causal expansion, reactivación selectiva y navegación sin reconstruir todo el historial.

## Objetivo

Determinar primero si las primitives actuales ya satisfacen materialmente la intención histórica bajo otra arquitectura. Sólo si existe gap real, extender la authority cognitiva existente para que ABOS pueda mantener múltiples contextos/ramas durables y activar progresivamente únicamente el subgrafo/contexto necesario, sin crear una segunda memoria ni inflar el prompt principal.

## Auditoría previa obligatoria

1. Mapear `ContextManager`, `MemoryRetriever`, `EnhancedRetriever`, `CompressionEngine`, `EventStream`, `KnowledgeStore`, ingestion y persistencia asociada.
2. Identificar si checkpoint/reset posee ruta real de restore/reactivation o sólo preserva recovery summary.
3. Buscar equivalentes semánticos de branch identity, parent/child context, active/dormant lifecycle, fork/merge/supersession y selective reactivation.
4. Seguir producers/consumers desde agent loop, goals/tasks, skills, world model y strategic planning.
5. Comprobar restart, stale context, conflicting branches, token budget y provenance.
6. Decidir explícitamente `NO_CHANGE | REUSE | EXTEND | UNIFY | MIGRATE | CREATE`; `CREATE` sólo si ninguna authority existente puede representar el contrato sin competir con P-020.

## Semántica objetivo

La forma exacta no está preimpuesta, pero la capacidad debe poder representar materialmente:
- contexto durable amplio fuera del working set;
- identidad y lineage de ramas/contextos cuando sean semánticamente distintos;
- estado active/dormant/superseded o equivalente no ambiguo;
- progressive disclosure por relevancia/objetivo/evidence, no por carga masiva;
- checkpoint y reactivación después de restart;
- expansión causal hacia parent/related context cuando haga falta;
- conflicto/version/provenance explícitos;
- presupuesto de contexto separado de pérdida de memoria.

Los nombres históricos `L0-L4` son intención de niveles/progresión, no obligación de reproducir exactamente cinco tablas o cinco clases si una arquitectura más simple demuestra equivalencia.

## Invariantes

- una sola authority lógica de memory/context; no second memory store;
- durable != prompt-resident;
- dormant != forgotten/deleted;
- checkpoint != branch si no existe identidad/reactivación correspondiente;
- compression no puede inventar hechos ni borrar provenance crítica;
- branch reactivation respeta token/context budget;
- restart no promociona contexto stale a vigente;
- world model, skill authority y task state siguen siendo responsabilidades distintas aunque se referencien desde memoria.

## Fallos/adversarial

Branch explosion, cycles de lineage, stale dormant branch reactivada como current truth, conflicting branches, checkpoint corrupto, restart durante fork/merge, summary que pierde autorización/commitment, token storm por expansión recursiva, duplicate branch por retry, branch deletion que elimina evidence todavía referenciada.

## Validación

Tests unit/integration y persistence/restart que demuestren, si la auditoría confirma gap:
- crear o identificar dos contextos materialmente distintos;
- mantener uno dormant sin cargarlo al working set;
- reactivarlo por necesidad/evidence;
- preservar lineage/provenance y estado tras restart;
- limitar expansión por budget;
- evitar duplicación tras retry/recovery;
- conservar compatibilidad con P-020 y consumers existentes.

Si source actual ya demuestra todo el objetivo bajo otra semántica, P-037 puede cerrar `NO_CHANGE` con equivalencia trazable y tests/evidencia existentes.

## Definition of Done

Existe evidencia trazable de una de dos condiciones:
1. la intención histórica de Branching Memory/progressive disclosure ya está materialmente satisfecha por authorities actuales y se documenta la equivalencia sin crear código; o
2. el gap real queda extendido sobre la authority P-020 existente y ABOS puede dormir/reactivar contextos durables selectivamente con lineage/provenance/restart/budget verificables.

P-037 no queda HECHO por existir compresión o checkpoints aislados.
